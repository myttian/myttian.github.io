- ==runc== : 命令行工具，`容器生成和运行工具`
- ==CRI==:  Container Runtime Interface （**容器运行时接口**）, Kubernetes定义的一组`与容器进行交互的接口`，只要实现了这个接口，就可以使用kublet来操作容器，对接到kubernetes平台上
- ==OCI:==  open Container Initiative 开放容器倡议, 即**容器规范标准**,   主要目的是为了`解决容器标准混乱`的问题
  - OCI提供了规范的一个实现，runc ，它可以直接使用容器，创建并运行它们等
  - runc的替代方案包括Kata-Runtime、GVisor和CRI-O
- ==容器运行时==： 运行和管理容器进程、镜像的工具
  - 低级别运行时：runc、lxc、gvisor、kata…（单纯的管理容器，无法管理镜像）
  - 高级别运行时：docker、containerd、podman、cri-o、rkt…（不仅可以管理容器也可以管理镜像）

- Libcontainer: 开源的==Linux容器管理库==，由Docker团队开发，用于支持Docker容器引擎的底层。Libcontainer提供了一个接口，使得应用程序可以直接访问Linux内核中的容器相关功能，例如命名空间、控制组、文件系统等。而命名空间（通过Linux Namespace）、控制组(Cgroups)、文件系统（rootfs）正是实现容器的核心
  - Namespace主要==实现访问隔离==，它是针对一类资源进行抽象，并将其进行封装提供给一个容器使用，因为每个容器都有自己独立的抽象，所以他们值之间是不可见的
  - Cgroup: control group, **控制组**，可以实现==将一组进程放进一个控制组==，通过给这个控制组分配对应的资源，从而实==现这个组下的资源控制==
- runC: ==基于Libcontainer的容器运行时工具==，它是Docker容器引擎的一个组件
  - runC利用Libcontainer提供的接口，将容器镜像转换为容器实例，并在隔离环境中启动容器进程。
  - runC还提供了对容器的生命周期管理，包括启动、停止、重启等。
  - 因此，可以说runC是Libcontainer的一个应用程序，==用于管理和运行容器==。同时，runC也是一个独立的开源项目，可以用于在各种容器环境中运行容器

  - 用包安装： rpm包、deb包
  - static binary bundles directly：二进制文件是静态链接,一个更加独立和可移植的解决方案，更方便；  而动态链接库，需要在运行时动态加载

  具体步骤： rpm

Define the Kubernetes version and used CRI-O stream

```sh
# 定义变量是为了repo源
KUBERNETES_VERSION=v1.30
PROJECT_PATH=prerelease:/main
```

Add the Kubernetes repository

```sh
cat <<EOF | tee /etc/yum.repos.d/kubernetes.repo
[kubernetes]
name=Kubernetes
baseurl=https://pkgs.k8s.io/core:/stable:/$KUBERNETES_VERSION/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/$KUBERNETES_VERSION/rpm/repodata/repomd.xml.key
EOF
```

Add the CRI-O repository

```sh
cat <<EOF | tee /etc/yum.repos.d/cri-o.repo
[cri-o]
name=CRI-O
baseurl=https://pkgs.k8s.io/addons:/cri-o:/$PROJECT_PATH/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/addons:/cri-o:/$PROJECT_PATH/rpm/repodata/repomd.xml.key
EOF
```

Install package dependencies from the official repositories

```sh
dnf install -y container-selinux
```

Install the packages

```sh
dnf install -y cri-o kubelet kubeadm kubectl
```

Start CRI-O

```sh
systemctl start crio.service
```

Bootstrap a cluster

```sh
swapoff -a
modprobe br_netfilter
sysctl -w net.ipv4.ip_forward=1

kubeadm init
```

==1、 CRI容器运行时接口==  

- K8s 定义的一组==与容器运行时交互==的接口，只要==实现了这套接口==的容器运行时都可以对接到 Kubernetes平台
- 不过 Kubernetes 推出 CRI 标准时没有现在的统治地位，所以有一些容器运行时可能不会自身就去实现 CRI 接口，于是就有了 `shim（垫片）`， 一个 shim 的职责就是==作为适配器将各种容器运行时本身的接口适配到 Kubernetes 的 CRI 接口==上，其中 `dockershim` 就是 Kubernetes 对接 Docker 到 CRI 接口上的一个垫片实现
- ==Kubelet== 通过 ==gRPC 框架==与容器运行时或 shim 进行通信，其中 ==kubelet 作为客户端==，CRI shim（也可能是容器运行时本身）作为服务器。 『我理解为**kubelet与docker、crio等容器运行时交互**』
- CRI 定义的 [API](https://github.com/kubernetes/kubernetes/blob/release-1.5/pkg/kubelet/api/v1alpha1/runtime/api.proto) 主要包括两个 gRPC 服务，`ImageService` 和 `RuntimeService`，`ImageService` 服务主要是拉取镜像、查看和删除镜像等操作，`RuntimeService` 则是用来管理 Pod 和容器的生命周期，以及与容器交互的调用（exec/attach/port-forward）等操作，可以通过 kubelet 中的标志 `--container-runtime-endpoint` 和 `--image-service-endpoint` 来配置这两个服务的套接字

==1、CNI==

CNI的接口并不是指HTTP，gRPC接口，==CNI接口是指对可执行程序的调用（exec)==。这些可执行程序称之为CNI插件

K8S节点默认的CNI插件路径为 ==/opt/cni/bin== ，在K8S节点上查看该目录，可以看到可供使用的CNI插件

个人理解：==容器运行时和网络插件==对接CNI标准

- 容器运行时通过==设置环境变量==以及从标准输入==传入的配置文件==来向插件传递参数

==CNI插件（容器网络接口）==分三种， Overlay隧道、路由、Underlay

- **隧道协议**：Overlay隧道， 主机之间创建隧道，将整个==容器网段的包==全都==封装成==底层的==物理网络中主机之间的包==

  - L2TP： 一种工业标准的Internet隧道协议， PPTP使用单一隧道，L2TP使用多隧道

    - 封装 ：将一种协==议承载在另一种协议中进行传输==的技术，如PPTP就是将PPP报文封装在GRE协议中。协议B（上面vpn基础里有报文图片）为被承载协议，GRE为承载协议

      隧道指被承载协议的传输通道

- **路由**：通信通过路由打通，无需在不同主机之间做一个隧道封包

- **Underlay**： ==容器和宿主机位于同一层网络==，两者拥有相同的地位。容器之间网络的打通主要依靠于底层网络

**CNI使用方法**：

- 在每个节点上配置 CNI 配置文件(/etc/cni/net.d/xxnet.conf)
- 安装 CNI 配置文件中所对应的二进制插件
- 在这个节点上创建 Pod 后，Kubelet 根据 CNI 配置文件执行前两步所安装的 CNI 插件； Pod 的网络就配置完成了

1. Install the operator on your cluster.

   ```sh
   # 启用operator资源清单文件
   kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/tigera-operator.yaml
   ```

   

2. Download the custom resources necessary to configure Calico.

   ```sh
   # 通过自定义资源方式安装
   curl https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/custom-resources.yaml -O
   ```

   

   toIf you wish to customize the Calico install, customize the downloaded custom-resources.yaml manifest locally.

3. 修改文件 `vi custom-resources.yaml`，修改为使用kubeadm init --pod-network-cidr对应的ip段

   ```yaml
    ipPools:
       - name: default-ipv4-ippool
         blockSize: 26
         cidr: 10.244.0.0/16
         encapsulation: VXLANCrossSubnet
   ```

4. Create the manifest to install Calico.

   ```
   kubectl create -f custom-resources.yaml
   
   kubectl delete -f custom-resources.yaml
   ```

## Deb822格式

**Types**：指定存储库的格式。 deb 表示存储库包含已预编译并准备安装的二进制包。 deb-src 表示需要编译的源代码包。

**URIs**：统一资源标识符，指定 APT 系统获取包的位置。

```sh
# http://us.archive.ubuntu.com/ubuntu/ 指向 Ubuntu 软件包存档的美国镜像，托管大量与 Ubuntu 兼容的软件
# http://security.ubuntu.com/ubuntu/ 专门用于安全更新。它是确保您的系统免受已知漏洞影响的关键资源
```

**Suites**:套件是指与 Ubuntu 发布周期的不同版本或阶段相一致的特定软件包集。例如，

- noble、noble-updates 和 noble-backports 链接到代号为“Noble”的版本，每个套件都有不同的用途：
  - noble 包含初始版本中包含的软件包
  - noble-updates 包含首次发布后发布的更新包，以解决错误或较小的增强功能
  - noble-proposed 预发布软件源
  - noble-backports 提供对某些软件包的较新版本的访问，这些软件包已向后移植以与“Noble”一起使用
- noble-security 专门用于解决“Noble”版本的安全漏洞的更新

**Components**:组件是存储库中的类别，按其支持状态或许可来组织软件包：

- main 包含 Ubuntu 支持的免费开源软件
- restricted 包含 Ubuntu 支持的专有驱动程序和软件
- universe 包括社区维护的免费和开源软件
- multiverse 的软件可能不是免费或开源的，并且不受 Ubuntu 官方团队的支持

**Signed-By**:此行指向包含用于验证包真实性的公钥的密钥环文件。指定的文件 /usr/share/keyrings/ubuntu-archive-keyring.gpg 包含官方 Ubuntu 存档签名密钥。验证软件包可确保它们未被篡改并且可以安全安装。

用以上措施可以进行定制的软件管理，从而能够安装满足特定需求或偏好的软件，增强系统安全性，并确保 Ubuntu 系统上的软件是最新的并按预期运行。

## cgroup

[CGroup 驱动程序 systemd 和 cgroupfs](https://baijiahao.baidu.com/s?id=1799249210398206218&wfr=spider&for=pc)   [cgroupfs](https://www.baidu.com/s?ie=UTF-8&wd=cgroupfs) 

**Cgroups（Control Groups）**是 Linux 内核的一个特性，用于对进程组进行资源限制和优先级分配。Cgroups 通过两种不同的**驱动程序**来实现：**systemd** 和 **cgroupfs**

-  **cgroupfs** 是 Linux 内核提供的 **Cgroups** 接口的原始实现，它以文件系统的形式挂载到用户空间（通常是 **/sys/fs/cgroup**）
-  **systemd** 是 Linux的一个初始化系统和服务管理器，它也提供了 Cgroups 的管理功能
