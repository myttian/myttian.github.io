> **K8s集群架构**

**小结：**

- 节点： 虚拟机或物理计算机
- pod： 一个工作节点可以有多个 pod
- 容器：一个 Pod 包含多个容器

master
主节点，控制平台，不需要很高性能，不跑任务，通常一个就行了，也可以开多个主节点来提高集群可用度。

worker
工作节点，可以是虚拟机或物理计算机，任务都在这里跑，机器性能需要好点；通常都有很多个，可以不断加机器扩大集群；每个工作节点由主节点管理

**Pod**

豆荚，K8S 调度、管理的最小单位，==一个 Pod 包含一个或多个容器==，每个 Pod 有自己的虚拟IP。==一个工作节点可以有多个 pod==，主节点会考量负载自动调度 pod 到哪个节点运行

> **K8s组件**

`kube-apiserver` 	API 服务器，公开了 Kubernetes API; ==提供对外接口，用来控制集群==
`etcd` 			  K8s==键值对数据库==，可以作为保存 Kubernetes 所有集群数据的后台数据库
`kube-scheduler` 	调度 Pod 到哪个节点运行
`kube-controller`    集群控制器
`cloud-controller`   ==云控制中心==； 与云服务商交互
`c-m`				控制中心

**Node 组件**
`kube-proxy`		 维护节点上的网络规则, 允许从集群内部或外部的网络会话与 Pod 进行网络通信
`kubelet`			在每个节点（node）上运行。 它==保证容器都运行在 Pod 中==

## 3、裸机安装（Bare Metal）

至少需要==两台机器（主节点、工作节点个一台）==，需要自己安装 Kubernetes 组件，配置会稍微麻烦点。
可以到各云厂商按时租用服务器，费用低，用完就销毁。
缺点：配置麻烦，缺少生态支持，例如负载均衡器、云存储

> **裸机安装**

**主节点需要组件**

- docker（也可以是其他容器运行时）
- kubectl 集群命令行交互工具
- kubeadm 集群初始化工具,  会安装集群控制台 Control plane

**工作节点需要组件** [文档](https://kubernetes.io/zh/docs/concepts/overview/components/#node-components)

- docker（也可以是其他容器运行时）
- kubelet 管理 Pod 和容器，确保他们健康稳定运行。
- kube-proxy 网络代理，负责网络相关的工作

```yaml
apiVersion: apps/v1
kind: Deployment	# 要定义的资源类型
metadata: 			# Deployment的信息（元数据），例如其名称和标签
  name: nginx-deploy
  labels:
    release: nginx_v1.22
spec:				# Deployment的具体规范
  replicas: 1
  strategy:			# 要使用的部署策略
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
      maxSurge: 25%
  # 选择由此Deployment管理的Pod的标签,用来查找关联的Pod，所有标签都匹配才行
  selector:			# 标签判断哪个pod归自己管理
    matchLabels:
      app: nginx
  template:			# 指定用于创建副本的Pod模板,包括Pod的元数据和容器规范
    metadata:
      labels:
        app: nginx
    spec:
      containers:	# 指定要在Pod中运行的容器
      - name: mynginx
        image: nginx:1.22.1
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080
  selector:			# 选择具有指定label标签的pod作为管理范围
    app: nginx
```

### ReplicaSet

帮助用户管理无状态的pod资源，精确反应用户定义的目标数量，但是RelicaSet不是直接使用的控制器，而是使用Deployment。

- Deployment: 工作在ReplicaSet之上，用于管理无状态应用，目前来说最好的控制器。支持滚动更新和回滚功能，还提供声明式配置
- DaemonSet： 用于确保集群中的每一个节点只运行特定的pod副本，通常用于实现系统级后台任务。比如ELK服务。特性：服务是无状态的；服务必须是守护进程
- Job： 只要完成就立即退出，不需要重启或重建
- Cronjob： 周期性任务控制，不需要持续后台运行
- StatefulSet： 管理有状态应用

ssl工作过程分为3阶段：

1. ==握手==：  3步：建立tcp连接、验证服务端身份、分发通信主密钥
   1. 验证服务端身份： **1**、client向svc发送一个hello报文，svc用其证书回应，这个证书是经过权威机构认证的，一个==实体与其公钥的绑定==，cli收到svc证书后，完成svc身份验证； **2**、cli==从证书中提取svc的公钥==，并随机生成一个==通信主密钥MS==； **3、**然后用svc的公钥对其进行加密后发送给svc，svc用自己的==私钥解密得到主密钥ms==，现在cli和svc都有ms了，有了ms，随后的数据加密和验证过程就好办了
   2. *公钥用来加密相当于锁*,私钥解密相当于钥匙
   3. 非对称加密更加安全，但是对称加密算法比非对称加密算法快大约1500倍。拥有更大的性能优势; **一般结合使用**
   4. 对称加密：加密解密都用这个密钥
   5. 非对称加密：用公钥加密可用私钥解密，用私钥加密可用公钥解密（签名）; 非对称除了应用于加密，还可用于==签名==
      1. 签名：a把文件发给b，a突然说：文件不是我发的，b要证明是a发的，就要用到签名
      2. 总结：==公钥加密，私钥解密；私钥签名，公钥验签==
      3. ==CA==：==受信任的公钥==； 公钥被黑客掉包，加密的文件被黑客得到，黑客可以用私钥解密，由于公钥不可靠，出现了ca机构，证书授权中心
         1. ca机构把用户的公钥做认证，盖一个ca机构的章，证明a的公钥是经过ca认证过的，就可以放心的去用公钥，ca机构用自己的私钥签名，ca签名过的数据就叫做证书   `certmgr.msc`
         2. 
2. ==密钥导出==
   1. 通信双方以相同的方法，用==主密钥ms生成4个密钥==
   2. 会话加密密钥：用来加密传输数据的对称密钥
   3. 会话mac密钥：mac报文鉴别码，检验报文完整性的技术

==Helm 3 与 Helm 2 的区别==  [Helm3移除了tiller](https://blog.csdn.net/qq_51545656/article/details/136648792) 

- Helm 2：在 Helm 2 中，采用了客户端-服务器模型，其中客户端是 Helm，服务器端是 Tiller。Tiller 作为 Kubernetes 集群中的一个 Deployment 运行，负责管理 Helm 的 Release 和执行 Kubernetes 操作。
- Helm 3：Helm 3 移除了 Tiller，简化了架构。现在，Helm 客户端直接与 Kubernetes API 服务器通信，执行所有的 Kubernetes 操作。这减少了复杂性，并提高了安全性，因为不再需要在集群中运行一个具有广泛权限的 Tiller 服务

**介绍**

Ingress 为外部访问集群提供了一个 **统一** 入口，避免了对外暴露集群端口；
功能类似 Nginx，可以==根据域名、路径==把请求转发到不同的 Service。可以配置 https



**使用**

- 要使用 Ingress，需要一个==负载均衡器 + Ingress 和 Controller== ，ingress要配置一个Controller去执行逻辑

- 裸机（bare metal) 搭建的集群，需要装负载均衡插件，可以安装 [METALLB](https://metallb.universe.tf/)

**正反代理**

正向代理和反向代理的主要区别在于它们==所代理的对象以及使用的场景不同==。

- ==代理对象不同==。正向代理是代表客户端，客户端向代理服务器发送请求并指定目标服务器，代理服务器将请求转发给目标服务器，并将响应返回给客户端；反向代理是代表服务端，客户端向反向代理服务器发送请求，反向代理服务器将请求转发给目标服务器，并将响应返回给客户端。
- ==场景不同==。正向代理常用于客户端无法直接访问某些资源时，例如科学上网、加速、访问缓存数据和隐藏后端；反向代理常用于保护服务器和负载均衡。
- 负载均衡和安全性不同。正向代理不会对客户端发出的请求进行拦截或修改，可以隐藏客户端的真实IP地址和身份信息；反向代理可以实现负载均衡、缓存、SSL加密等操作，提高服务器的性能和安全性

## Kong

[分布式 API 网关 Kong网关简介 ](https://zhuanlan.zhihu.com/p/531804692) [Kong ](https://www.jianshu.com/p/b44400618c69) [Kong ](https://baijiahao.baidu.com/s?id=1682207939657360739&wfr=spider&for=pc) [kong原理及使用](https://blog.51cto.com/voice/5524786)  

**Kong主要有三个组件：**

1. Kong Server ：基于nginx的服务器，用来接收API请求。
2. Apache Cassandra/PostgreSQL ：用来存储操作数据。
3. Kong dashboard：官方推荐UI管理工具，也可以使用 restfull 方式 管理admin api

Kong 是一个开源的微服务网关，但又不只是一个网关，它还集成了服务注册和发现、负载均衡、健康检查等功能，不需要单独部署和维护其它的功能组件，大大降低了维护成本。

同时 Kong 通过插件来提供限流、熔断、监控、日志等能力，将原本需要在代码中完成的功能全部移到 Kong 服务端完成，减少了对服务本身代码的侵入，代码改造成本大大降低。

在 Kong 的微服务架构中，Kong 担当了注册中心的角色，服务提供者（Provider）首先将服务信息注册到 Kong，服务消费者（Consumer）调用服务的过程是调用端先将请求发到 Kong，再通过 Kong 把请求转发到服务提供者而实现间接调用
