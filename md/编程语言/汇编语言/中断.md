# 入口地址

## 程序入口地址

> 问题： windows程序执行时,系统如何找到入口地址

Windows 程序执行时，系统定位入口地址并非简单地读取一个固定偏移量，而是一个涉及 **PE 文件格式解析、加载器重定位、以及运行时库初始化** 的多级跳转过程。

以下是系统从加载到最终执行用户代码的完整链路：

### 1. 核心数据结构：PE 头中的 Entry Point

Windows 可执行文件遵循 PE (Portable Executable) 格式。系统在加载程序时，首先会解析以下关键结构：

```text
IMAGE_DOS_HEADER → e_lfanew (指向 NT Headers)
    └─ IMAGE_NT_HEADERS
        ├─ FileHeader
        └─ OptionalHeader
            └─ AddressOfEntryPoint (RVA) ← 这就是"入口地址"
```

- **AddressOfEntryPoint**: 这是一个 **RVA**，即相对于模块加载基址的偏移量，而非绝对虚拟地址。
- **ImageBase**: `OptionalHeader` 中声明的首选加载基址（如 64位程序通常为 `0x140000000`）。

> ⚠️ **关键点：** 如果由于 ASLR 或地址冲突导致模块未加载到首选基址，加载器会对整个镜像进行 **重定位**，此时实际入口 VA = 实际加载基址 + AddressOfEntryPoint。

### 2. 真实执行流程：三级跳转链

`AddressOfEntryPoint` 指向的通常 **不是** 你的 `main()` 或 `WinMain()` 函数，而是 C/C++ 运行时库的启动代码。完整的调用链如下：

```
操作系统加载器 (ntdll!LdrInitializeThunk)
    │
    ▼
① PE Header 指定的 EntryPoint (CRT Startup Code)
    │  例如: mainCRTStartup / wWinMainCRTStartup
    │  作用: 初始化全局变量、堆、TLS、调用C++构造函数
    ▼
② CRT 初始化完成后的回调
    │  调用 __scrt_common_main_seh() 等内部函数
    ▼
③ 用户定义的入口函数
       main() / wmain() / WinMain() / wWinMain() / DllMain()
```

#### 不同程序类型的默认入口符号

| 程序类型              | 链接器默认入口符号   | 对应源码入口           |
| --------------------- | -------------------- | ---------------------- |
| GUI (.exe)            | `wWinMainCRTStartup` | `wWinMain` / `WinMain` |
| Console (.exe)        | `mainCRTStartup`     | `main` / `wmain`       |
| DLL                   | `_DllMainCRTStartup` | `DllMain`              |
| 无CRT (/NODEFAULTLIB) | 直接指向用户函数     | 自定义入口             |

### 3. 加载器的具体操作步骤

当 `CreateProcess` 被调用后，内核和 `ntdll.dll` 协作完成以下工作：

1. **映射镜像**: 将 PE 文件各 Section 按对齐粒度映射到虚拟内存。
2. **处理重定位表**: 若实际基址 ≠ ImageBase，遍历 `.reloc` 段修正所有绝对地址引用。
3. **解析导入表**: 遍历 `.idata` 段，加载依赖 DLL 并填充 IAT。
4. **执行 TLS 回调**: 在 EntryPoint 之前，先执行所有 TLS Callback 函数（常用于反调试）。
5. **跳转到 EntryPoint**: 设置 EAX/RAX = 模块句柄，然后 `jmp` 到计算出的入口 VA。
6. **CRT 接管**: 启动代码完成运行时环境初始化后，才调用用户的 `main/WinMain`。

### 4. 特殊情况与注意事项

- **ASLR 影响**: 开启 ASLR 后，每次启动的实际入口 VA 都不同，但 RVA 恒定。调试器显示的入口地址是重定位后的结果。
- **自定义入口点**: 可通过链接器选项 `/ENTRY:MyEntry` 绕过 CRT 直接指定入口，但需自行处理所有初始化，否则全局变量、浮点运算、异常处理等均不可用。
- **.NET 程序**: PE 头的 EntryPoint 指向 CLR 引导桩代码，真正的托管入口由元数据中的 `MethodDef` 表指定，由 CLR JIT 编译后才执行。
- **壳/加壳程序**: 加壳工具会修改 `AddressOfEntryPoint` 指向解包代码，原始入口被加密存储，解密还原后再跳回真实 CRT 入口。

### 快速验证

你可以使用以下工具观察真实的入口地址：

- **dumpbin /headers app.exe** → 查看 `AddressOfEntryPoint` RVA
- **x64dbg / IDA** → 动态调试时断在系统断点，单步跟踪可看到完整的 CRT → main 跳转链
- **link /VERBOSE app.obj** → 链接时输出显示解析到的实际入口符号名

总结来说，系统通过 PE 头找到的是 **CRT 启动代码的 RVA**，经过加载器重定位得到实际 VA，再由 CRT 完成运行时初始化后，才最终到达程序员编写的入口函数。

## windows程序安装过程本质是进行什么操作

Windows 程序安装过程的本质，并不是简单的“文件复制”，而是一个**将软件资源与 Windows 操作系统环境进行深度集成和注册的过程**。

其核心目的是让操作系统知道“这个软件存在”、“它在哪里”、“如何运行它”以及“如何卸载它”。具体来说，安装过程主要执行了以下几类关键操作：

### 1. 文件系统的部署与结构化

这是最基础的操作，但不仅仅是拷贝：

- **释放文件：** 将压缩包（如 .cab, .msi 内部流）解压，将可执行文件、动态链接库、资源文件等写入磁盘。
- **目录规范化：** 遵循 Windows 文件系统规范，将文件放置在特定位置（如 `Program Files`、`AppData`、`System32` 等），并设置正确的访问控制列表权限。
- **依赖库部署：** 检查并安装共享组件（如 Visual C++ Redistributable, .NET Runtime, DirectX），防止“DLL地狱”。

### 2. Windows 注册表写入（核心灵魂）

这是 Windows 安装区别于单纯文件复制的**最关键特征**。安装程序会向注册表数据库写入大量键值：

- **卸载信息：** 在 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` 下创建条目，记录卸载命令、版本号、安装路径等，使程序出现在“设置 > 应用”列表中。
- **COM/ActiveX 注册：** 如果软件包含 COM 组件，需注册 CLSID、ProgID 和类型库，以便系统能通过 GUID 调用这些组件。
- **文件关联：** 建立扩展名（如 `.psd`）与应用程序的映射关系，定义默认图标和处理程序。
- **全局配置：** 写入许可证信息、用户偏好、硬件驱动参数等持久化状态。

### 3. 系统集成与入口点创建

让软件能够被用户或系统触发：

- **快捷方式：** 在开始菜单、桌面、任务栏创建 `.lnk` 文件。
- **环境变量：** 修改 `PATH` 变量，使命令行工具可在任意路径下被调用。
- **服务与计划任务：** 注册后台服务或定时任务，实现开机自启或周期性执行。
- **Shell 扩展：** 注入右键菜单、文件资源管理器预览窗格等 UI 钩子。
- **驱动加载：** 对于硬件相关软件，通过 PnP 管理器安装并加载内核级驱动程序。

### 4. 事务性与回滚机制（现代安装器特有）

专业的安装框架（如 MSI/WiX, InstallShield）具备**原子性**：

- **系统还原点：** 在安装前创建快照。
- **事务日志：** 记录每一步操作。如果安装中途失败，安装器会根据日志逆向执行操作（删除已拷文件、恢复注册表），保证系统不会处于“半装不装”的损坏状态。

### 5. 验证与安全检查

- **数字签名验证：** 确认安装包来源可信且未被篡改。
- **UAC 提权：** 请求管理员权限以修改受保护的系统区域。
- **兼容性检测：** 检查 OS 版本、架构（x64/ARM64）、前置依赖是否满足要求。

---

### 总结对比

| 操作类型           | 绿色软件 / 便携版 | 正式安装版    |
| ------------------ | ----------------- | ------------- |
| 文件复制           | ✅                 | ✅             |
| 注册表写入         | ❌ (极少)          | ✅  **(核心)** |
| 系统服务/驱动      | ❌                 | ✅             |
| 文件关联/Shell扩展 | ❌                 | ✅             |
| 标准卸载支持       | ❌                 | ✅             |
| 多用户支持         | ❌                 | ✅             |

> **⚠️ 注意：** 正因为安装过程涉及大量底层系统修改，这也是为什么恶意软件常伪装成安装程序——它们利用同样的机制（注册表自启动、服务注入、驱动加载）来实现持久化驻留。反之，这也是为什么直接删除安装文件夹往往无法彻底卸载软件，因为注册表和系统深处的残留并未被清理。

简而言之，Windows 程序安装的本质是  **“文件部署 + 系统状态变更 + 契约注册”**  的组合过程。

## 绿色软件比安装版少了哪些步骤

绿色软件（Portable/Green Software）之所以“绿色”，正是因为它**刻意省略**了安装版中所有涉及“系统级修改”和“持久化集成”的步骤。

具体来说，相比标准安装版，绿色软件主要少了以下五大类核心操作：

### 1. 省略了 Windows 注册表写入

这是两者最本质的区别。绿色软件完全不触碰（或仅极少触碰）注册表：

- **无卸载信息注册：** 不会在 `HKLM\...\Uninstall` 下创建条目，因此不会出现在 Windows “设置 > 应用”列表中，也无法通过系统标准接口卸载。
- **无 COM/ActiveX 注册：** 不注册全局 CLSID、类型库或 ProgID。如果软件依赖 COM 组件，通常采用“免注册 COM”技术（如 SxS 并行程序集清单）或在运行时动态加载。
- **无全局文件关联：** 不会将 `.xyz` 扩展名绑定到该软件。打开文件通常需要手动拖入或通过软件内部的文件浏览器。
- **无 Shell 扩展注入：** 不会添加右键菜单项、资源管理器预览窗格或缩略图处理器。

### 2. 省略了系统目录与权限修改

绿色软件遵循“自包含”原则，不对系统区域进行写操作：

- **不写入 System32/SysWOW64：** 所有依赖的 DLL、运行时库都放在软件自身目录下，避免污染系统目录或引发 DLL 地狱。
- **不修改全局环境变量：** 不会向系统 `PATH` 中添加路径。命令行调用需指定完整路径或手动配置。
- **无需管理员权限：** 由于不修改受保护的系统目录和注册表，通常无需 UAC 提权即可运行（除非软件本身功能需要）。
- **配置文件本地化：** 将配置保存在软件目录下的 `.ini`、`.json` 或便携版 AppData 中，而非写入 `%APPDATA%` 或注册表，实现“拷走即用”。

### 3. 省略了系统集成入口点

绿色软件是“被动”存在的，不主动融入系统交互流：

- **无开始菜单/桌面快捷方式：** 不自动创建任何 .lnk 文件，需用户手动建立。
- **无服务与计划任务注册：** 不以 Windows Service 或 Task Scheduler 形式驻留后台，无法实现开机自启或定时执行（除非借助第三方工具）。
- **无驱动安装：** 不包含内核级驱动部署流程。若需硬件访问，通常依赖用户模式 API 或要求用户预先安装驱动。
- **无防火墙/网络策略自动配置：** 不会自动添加 Windows 防火墙规则。

### 4. 省略了安装器事务机制

绿色软件没有“安装过程”，自然也没有安装器的安全保障：

- **无原子性保证：** 不存在 MSI/WiX 的事务日志和回滚机制。如果解压或复制中途失败，可能留下不完整文件，需手动清理。
- **无系统还原点：** 不会在安装前创建快照。
- **无依赖自动检测与安装：** 不会自动检查并安装 .NET、VC++ Runtime 等前置条件，缺失时直接报错，需用户自行解决。

### 5. 省略了多用户与许可管理

- **无 per-machine / per-user 区分：** 不区分“为所有用户安装”还是“仅为当前用户安装”，配置对所有使用者相同（或按启动账户隔离）。
- **无集中式许可证存储：** 激活信息通常保存在本地文件中，不支持域环境下的批量授权管理。

---

### 对比速查表

| 操作步骤           | 安装版                   | 绿色版           | 影响                 |
| ------------------ | ------------------------ | ---------------- | -------------------- |
| 注册表写入         | ✅ 大量                   | ❌ 几乎无         | 绿色版不留系统痕迹   |
| 系统目录写入       | ✅ Program Files/System32 | ❌ 仅自身目录     | 绿色版不污染系统     |
| 文件关联/Shell扩展 | ✅ 自动注册               | ❌ 无             | 绿色版需手动打开文件 |
| 服务/自启动        | ✅ 可注册                 | ❌ 无             | 绿色版无后台驻留     |
| 卸载支持           | ✅ 标准卸载               | ❌ 删除文件夹即可 | 绿色版清理更简单     |
| 管理员权限         | ✅ 通常需要               | ❌ 通常不需要     | 绿色版权限更低更安全 |
| 依赖自动安装       | ✅ 内置检测               | ❌ 需手动处理     | 绿色版上手门槛略高   |

> **核心洞察**
> 绿色软件的本质是  **“以功能完整性换取系统零侵入”** 。它把原本由操作系统承担的“集成、注册、调度”职责，全部内化为软件自身的逻辑（如用配置文件替代注册表、用相对路径替代环境变量、用免注册COM替代全局注册）。

这也解释了为什么某些复杂软件（如大型 IDE、专业设计工具、杀毒软件）**无法做成真正的绿色版**——它们的功能深度依赖系统级钩子、驱动、服务和全局注册，剥离这些集成就等于剥离了核心能力。

# BIOS

## BIOS与CMOS区别

[BIOS与CMOS区别](https://blog.csdn.net/weixin_39718006/article/details/113046870)  

> BIOS中断例程: 固化在ROM
>
> 可读写的CMOS RAM芯片： 系统设置程序，用来设置BIOS
>
> - 加电后，对设备自检，POST(Power On Self Test,上电自检)
> - POST自检后，ROM BIOS将按照系统CMOS设置中的启动顺序引导，读入操作系统引导记录，然后将系统控制权交给引导记录，由引导记录完成系统的启动

BIOS 和 CMOS 是计算机主板上两个紧密相关但**本质完全不同**的概念。简单来说：**BIOS 是“程序”（软件），CMOS 是“数据仓库”（硬件）。**

以下是它们各自的功能详解及相互关系：

### 1. BIOS 的功能

**BIOS** 是固化在主板上只读存储器芯片中的一组固件程序。它是计算机启动后运行的第一个软件，充当操作系统与硬件之间的桥梁。

- **加电自检：** 开机时自动检测 CPU、内存、显卡、键盘等关键硬件是否正常。若发现致命错误，会通过蜂鸣器报警或屏幕提示阻止启动。
- **系统引导加载：** 按照预设的启动顺序（如 NVMe SSD → USB → 网络）查找引导记录，将控制权移交给操作系统的引导程序。
- **硬件初始化与配置：** 在 OS 加载前，初始化主板芯片组、设置内存时序、配置 PCIe 通道、启用/禁用集成设备等，为系统提供标准化的硬件抽象层。
- **提供底层中断服务：** 为早期的 DOS 或实模式程序提供标准的硬件调用接口（现代 OS 进入保护模式后通常不再使用）。
- **Setup 配置界面：** 提供用户可操作的图形或文本界面，用于修改系统参数。**注意：这个界面本身是 BIOS 程序的一部分，但修改后的参数并不保存在 BIOS 芯片中。**
- **固件更新支持：** 现代 UEFI BIOS 支持通过 U 盘或网络在线刷新自身固件。

**现代演进：** 传统 Legacy BIOS 已逐渐被 **UEFI** 取代。UEFI 支持 GPT 分区表、大于 2TB 硬盘启动、图形化鼠标操作、安全启动和网络栈，但其核心职责（POST + Boot + Runtime Services）与 BIOS 一脉相承。

### 2. CMOS 的功能

**CMOS** 本意是指一种低功耗半导体制造工艺，在 PC 语境下特指主板上的一块**易失性 RAM 芯片**（现代主板多集成在南桥/PCH 内部）。它唯一的功能就是**存储数据**。

- **存储 BIOS 设置参数：** 保存用户在 BIOS Setup 中修改的所有配置，包括：
    - 系统日期和时间
    - 启动设备优先级
    - 内存 XMP/EXPO 配置文件选择
    - CPU 超频电压与倍频
    - 风扇曲线策略
    - 安全启动密钥状态
    - 唤醒定时器、密码等
- **维持实时时钟运行：** 配合主板上的纽扣电池，在计算机关机断电后继续为 RTC 电路供电，确保时间和 BIOS 设置不丢失。
- **存储硬件校验信息：** 部分主板用 CMOS 存储上次成功启动的配置哈希值，用于“启动失败自动回退”机制。

**⚠️ 关键特性：** CMOS RAM 是**易失性存储器**，一旦断电且电池耗尽/移除，所有数据立即丢失，BIOS 设置将恢复出厂默认值。这就是为什么扣电池能“重置 BIOS”。

### 3. 两者的关系：程序 vs 数据

| 对比维度     | BIOS / UEFI                                | CMOS                          |
| ------------ | ------------------------------------------ | ----------------------------- |
| **本质**     | 固件程序                                   | 易失性 RAM 存储单元           |
| **存储介质** | SPI Flash ROM（非易失）                    | SRAM（易失，靠电池维持）      |
| **内容**     | 代码（POST、引导、Setup UI）               | 数据（用户设置、时间）        |
| **断电后**   | 永久保留                                   | 丢失（除非有电池）            |
| **用户操作** | “进入 BIOS”实际是运行 BIOS 中的 Setup 程序 | “清除 CMOS”实际是清空这块 RAM |
| **容量**     | 数 MB ~ 数十 MB                            | 通常仅 256B ~ 8KB             |

### 常见误区澄清

- **“进 BIOS 改设置”**  → 准确说法是“运行 BIOS 固件中的 Setup 程序，将新参数写入 CMOS RAM”。
- **“刷 BIOS”**  → 更新的是 Flash ROM 中的固件代码，**不影响** CMOS 中的用户设置（但版本变更可能导致旧设置不兼容而被自动重置）。
- **“CMOS 电池没电了”**  → 影响的是 CMOS 数据保持能力，BIOS 程序本身完好无损，换电池后重新设置即可。
- **“BIOS 坏了”**  → 指固件损坏，通常需要编程器重刷或双 BIOS 切换恢复，与 CMOS 无关。

简而言之：**BIOS 是大脑（知道怎么做），CMOS 是记事本（记住你的偏好）。** 没有 BIOS，电脑无法启动；没有 CMOS（或电池失效），电脑仍能启动，但每次都会回到出厂默认状态并可能报时间错误。

## UEFI固件

主板上的UEFI固件主要存储在SPI Flash芯片中，这是一种非易失性存储器，断电后数据不会丢失。

### 芯片类型与规格

1. 芯片类型：现代主板几乎都用SPI NOR Flash，支持XIP（就地执行），CPU可直接运行其中代码，无需先拷贝到内存。
2. 常见品牌：Winbond（华邦）、MXIC（旺宏）、Macronix、GigaDevice等。
3. 容量大小：现代UEFI固件通常占用16MB到32MB，部分服务器或高端主板可达64MB，远大于传统BIOS的1-2MB。

### 芯片位置

芯片通常位于主板上靠近PCH（南桥） 的位置，板子上往往印有“BIOS”或“UEFI”字样标记。

> 传统老主板用ROM或EEPROM存储BIOS，而UEFI时代基本全面转向SPI Flash，容量更大、读写更方便，也支持刷写升级。

端口和接口这两个词经常混着用，但严格来说，它们是两个层面的概念：端口更偏“逻辑通道”，接口更偏“物理或软件契约”。简单理解，端口是“门牌号”，用来区分不同的服务；接口是“门”，是连接和交互的规则或实体。

### 核心区别

1. 端口（Port）：主要是逻辑概念，用在网络通信里，用来区分同一台设备上不同的服务或程序。比如浏览网页用的80端口、远程登录用的22端口。
2. 接口（Interface）：范围更广，可以是物理实体（比如USB口、网线口），也可以是软件协议（比如API接口），是设备或组件之间交互的连接点。

### 计算机硬件里的“端口”和“接口”

在计算机硬件领域，这两个词经常被混用，但本质上指的是不同的东西：

- 接口：是CPU和外部设备之间沟通的整个电路，负责协调速度、转换信号、处理协议，比如USB控制器、显卡接口。
- 端口：是接口电路里面具体可寻址的寄存器。一个接口（比如一个串口）会包含多个端口（数据端口、状态端口、命令端口），每个端口有唯一的地址，CPU就是通过这些地址来读写数据的。

> 可以这样理解：接口是一个“办事处”，端口是办事处里的“窗口”，CPU办事要找对窗口才能高效处理。

### 网络里的“端口”

网络里的端口一般指逻辑端口，是一个数字（0~65535），用来标识设备上的具体服务：

1. 公认端口（0~1023）：绑定常见服务，比如80端口是HTTP网页服务，21端口是FTP文件传输，443端口是HTTPS加密网页。
2. 注册端口（1024~49151）：分配给公司和开发者的特定应用，比如MySQL数据库默认3306端口。
3. 动态/私有端口（49152~65535）：客户端程序临时分配的端口，用来和服务器通信。

### 一个容易混淆的地方

“端口”在硬件语境下也常指物理插孔，比如“USB端口”“网线端口”。 这时候它和“物理接口”基本是同义词，但“接口”的涵盖面更广，还包含软件层面的概念（如API）。 所以具体含义要结合语境判断。

USB 本身是串行总线，没有传统意义上的“位宽”，它不是一次传输多少位并行数据的概念。你问到“位”，其实对应的是它的地址空间，也就是一条 USB 总线上最多能挂多少个设备。

- 地址位数：USB 使用 7 位地址，理论上可分配 128 个地址（0~127），其中地址 0 保留给新接入设备做初始化，所以实际最多连接 127 个设备（包括集线器）。
- 传输方式：USB 是串行传输，信号线只有一对差分线，数据是一位一位发的，所以不按“8 位、16 位、32 位”来算。
- 物理引脚：不同版本的接口针脚数不同，比如 USB 2.0 是 4 针，USB 3.0 是 9 针，Type-C 是 24 针，这些属于接口定义，不是数据位宽。

> 需要区分一下：数据总线（比如 CPU 和内存之间的 64 位总线）才有明确的位宽概念，USB 属于外设总线，走的是串行协议，两者不是一回事。

是的，BCD码（二进制编码的十进制）在工业控制领域确实应用很广，它尤其适合需要精确显示和稳定传输的场景。

BCD码的核心优势：用4位二进制表示1位十进制数，能精确表达0.1这类二进制无法精确表示的十进制小数，而且和数码管这类显示设备天然匹配，调试时一眼就能看懂。

### 典型应用场景

1. 数码管/仪表显示：这是BCD码最经典的用途。PLC计算后，先把内部十六进制数据转成BCD码，再输出给数码管或液晶屏显示，比如电梯楼层、设备温度、转速表等。
2. PLC与现场设备通信：在Modbus、CANopen等工业总线协议中，BCD码常作为寄存器数据的标准格式。比如某个PLC的温度设定寄存器，文档会明确标注数据类型是BCD，范围0000~9999，这样上位机直接按BCD解析就能得到正确的十进制数值。
3. 实时时钟（RTC）：很多PLC和工业设备的时钟芯片，年月日时分秒都是按BCD码存储的，这样“23:59:59”下一秒进位到“00:00:00”的逻辑在硬件层面就能固定下来，不会出错。
4. 计量与金融设备：电表、水表、加油机这些受法规监管的设备，必须保证显示值和内部计数严格一致，BCD码的整数精度能避免浮点数带来的舍入误差，这是合规要求。

### 需要注意的地方

- 运算效率不高：BCD码占用空间比纯二进制多，运算时需要配套校正电路，所以不适合高速运算，它强在显示和传输，不在计算。
- 不同PLC有差异：比如西门子S7-1200/1500的BCD16范围是-999到+999，而S7-200和三菱的BCD16是0到9999，编程时要看清你用的PLC型号，否则转换会出错。

> ⚠️ 如果你在PLC里用BCD码做数据转换，先查一下所用PLC的BCD码范围和指令格式，不同品牌和系列可能不一样。

简单说，BCD码在工业控制里不是最“快”的，但它是和人类十进制习惯、显示设备最“合拍”的编码，所以一直没被淘汰。

以王爽《汇编语言》实验15为例——在屏幕中间依次显示“a”~“z”，按下Esc键后改变显示颜色，核心思路如下：

1. 保存原中断入口：将中断向量表中`[9*4]`和`[9*4+2]`处的原int 9入口地址保存到`ds:`和`ds:`中。
2. 设置新中断向量：将新int 9例程的偏移地址和段地址写入中断向量表。
3. 编写新中断例程：
   - 先用`in al,60h`读出扫描码；
   - 再模拟int指令调用原BIOS int 9（用`pushf`+修改IF/TF+`call dword ptr ds:`，因中断向量表已改，不能用`int 9`直接调用）；
   - 最后判断扫描码，若为Esc（扫描码1），修改显存中字符属性字节改变颜色。
4. 恢复原中断向量：程序结束前将保存的原入口地址写回中断向量表，否则键盘会异常。

> 这些键盘程序需在DOS实模式下运行，Windows 2000的DOS方式下会出现与硬件工作原理不符的现象。

### int 9与int 16h的配合

- int 9：硬件中断，按键时向键盘缓冲区写入数据。
- int 16h：软中断，应用程序调用时从缓冲区读取数据（功能号0），缓冲区空则循环等待。

两者写入和读取时机不同，int 9在按键时写入，int 16h在程序调用时读出，形成一对配合。

IRQ是中断请求，是硬件设备向CPU发出的“信号”；中断例程（ISR）是CPU收到信号后实际执行的代码。IRQ是“请求”，中断例程是“处理”，二者是触发与被触发的关系。

### 🔧 核心区别

1. 本质不同：IRQ是硬件信号或编号，由外设电路或中断控制器产生，代表“有设备要打扰CPU”；中断例程是一段函数代码，负责具体处理事件。
2. 产生方式不同：IRQ由硬件事件触发（如网卡收包、键盘按下），是异步的；中断例程由CPU响应IRQ后调用，是被动执行的。
3. 注册机制：驱动通过`request_irq()`把中断例程绑定到某个IRQ号上，IRQ是“钥匙”，中断例程是“锁对应的动作”。
4. 共享关系：一个IRQ号可以被多个设备共享，对应多个中断例程，通过`irqaction`链表串联；触发时内核遍历链表，依次调用所有注册的处理函数。

### ⚙️ 在Linux中的配合

- 每个IRQ对应一个`irq_desc`结构体，存储状态、锁和处理函数链表。
- 中断触发后，CPU通过中断控制器识别IRQ号，查中断向量表找到对应中断例程入口，保存现场后跳转执行。
- 中断例程分顶半部（快速、不可阻塞，只做应答和关键数据保存）和底半部（耗时逻辑如文件写入，交给工作队列或软中断），保证响应速度。

> 简单理解：IRQ是“门铃响了”，中断例程是“开门后做的事”。门铃本身不做事，但决定了你去开哪扇门。

📋 常见混淆点

- IRQ vs FIQ：ARM架构下FIQ是快速中断，优先级更高、有专用寄存器、不可屏蔽，响应更快；IRQ可被屏蔽，优先级较低。
- ISR vs 中断处理程序：严格来说，一条中断线对应一个中断处理程序（总入口），它再调用挂在该线上的多个ISR（具体设备处理函数）。

## dummy iret

[bios中断手册](https://jadeshu.blog.csdn.net/article/details/89036196)  [BIOS 中断向量表](https://jadeshu.blog.csdn.net/article/details/89036196)  

“dummy iret”是“虚拟中断返回”或“空中断返回”的意思，在汇编和底层调试场景中，指一个不执行实际中断返回逻辑的 IRET 指令，通常作为占位符或调试辅助使用。

结合你之前查的汇编中断相关概念，这个说法常见于Bochs{id="entity_1"}等模拟器的调试输出中。比如当调试器捕获到 `int 3` 断点或单步异常时，会打印类似 `INT03 >... BREAKPOINT ; dummy iret`，意思是模拟器内部用一条“空”的 IRET 来处理这个调试事件，而不是真正返回到被中断的程序。

### 拆开理解

1. IRET 本身：中断返回指令，执行时从堆栈弹出 IP、CS 和标志寄存器，恢复中断前的现场，让 CPU 回到断点继续执行。
2. dummy 的含义：意为“虚设的、假的、占位的”，表示这个指令不完成真实功能，只是走个过场。
3. 合在一起：在调试器或模拟器内部，当某个中断被捕获但不需要真正执行中断服务程序时，就用一条 dummy iret 来“假装”返回，保持栈和状态一致，避免程序跑飞。

> 简单说，它不是让你写代码时用的指令，而是调试器/模拟器内部的一种占位处理方式。你在写中断服务程序时，末尾仍需用真正的 `IRET` 来返回。

### dummy iret有多少个

“dummy iret”没有固定数量，它不是一个有明确计数的指令或对象，而是汇编/底层编程里的一种常见写法。

结合你之前查过的中断、iret、汇编内容，这里说的“dummy iret”通常指：一个什么都不做的空中断服务程序，里面只有一条 `iret` 指令，用来占位或兜底，让中断发生时CPU能安全返回，不产生实际效果。

具体出现场景：

- BIOS中断向量表：BIOS对很多中断向量都指向同一个 `dummy_iret_handler`，比如在Bochs里看到 `int 1`、`int 3`、`int 5` 等都指向 `00D1:1085` 或 `F000:FF53`，这些入口就是一条 `iret`，数量取决于有多少中断向量被默认填充。
- ST7单片机代码：在ST7的汇编例程里，`.dummy_rt`、`.dummy` 这类标号后跟 `iret`，用作未使用中断向量的默认处理，比如 `ffe4h`、`ffeeh` 等位置都指向 `dummy_rt`，具体个数由芯片的中断源数量决定。
- 自己写中断例程：写汇编程序时，为测试或占位，也可能临时定义一个只含 `iret` 的中断处理程序，数量完全由代码决定。

所以“有多少个”取决于具体环境——看BIOS或芯片的中断向量表里有多少个条目被指向这个空处理函数，而不是一个固定常数。若问某个具体环境（如Bochs的DOS、某款ST7芯片），可查对应中断向量表确认个数。
