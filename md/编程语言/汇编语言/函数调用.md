# call、ret

在计算机体系结构和汇编语言中，`call` 和 `ret` 是实现**函数调用（Function Call）**与**返回（Return）**的一对核心指令。它们共同维护了程序的执行流控制和栈（Stack）的平衡。

以下是它们的详细解析：

### 1. `call` 指令（调用）

`call` 用于跳转到一个子程序（函数）开始执行。它不仅仅是跳转，还必须“记住”回来的路。

- 核心操作：

  1. **压栈保存返回地址：** 将下一条指令的地址（即 `call` 之后那条指令的 EIP/RIP）推入栈中。
  2. **跳转：** 将程序计数器（EIP/RIP）修改为目标函数的入口地址。

- 伪代码逻辑：

  ```assembly
  push(next_instruction_address)
  jmp target_function
  ```

- 类型：

  - **近调用 (Near Call):** 在同一代码段内跳转，只压入偏移量（Offset/IP）。
  - **远调用 (Far Call):** 跨段跳转，同时压入代码段寄存器（CS）和偏移量（IP）。

### 2. `ret` 指令（返回）

`ret` 用于从子程序返回到调用者继续执行。它是 `call` 的逆操作。

- 核心操作：

  1. **弹栈恢复返回地址：** 从栈顶弹出之前由 `call` 压入的地址。
  2. **跳转：** 将弹出的地址加载回程序计数器（EIP/RIP），使CPU回到调用点之后的指令继续执行。

- 伪代码逻辑：

  ```text
  pop eip  ; 实际硬件中没有直接pop到eip的指令，这是逻辑描述
  ```

- 带参数的 ret (`ret n`)：

  - 形式如 `ret 4` 或 `ret 8`。
  - 在执行完普通的返回后，还会将栈指针（ESP/RSP）加上 `n`。
  - **用途：** 用于清理传递给函数的参数（常见于 Windows API 的 `stdcall` 调用约定）。

### 3. 关键配合机制：栈帧与调用约定

`call` 和 `ret` 的正确工作依赖于**栈的平衡**。如果 `call` 压入了返回地址，而 `ret` 弹出时栈顶不是这个地址，程序就会崩溃或跳转到错误位置。

| 特性           | call                  | ret                   |
| -------------- | --------------------- | --------------------- |
| **方向**       | 进入函数              | 离开函数              |
| **栈操作**     | PUSH 返回地址         | POP 返回地址          |
| **寄存器影响** | 修改 EIP/RIP, ESP/RSP | 修改 EIP/RIP, ESP/RSP |
| **配对要求**   | 必须有对应的 ret      | 必须对应之前的 call   |

### 4. ⚠️ 安全警示：ROP 攻击

理解 `call/ret` 对于理解现代安全漏洞至关重要：

- **缓冲区溢出与 ROP：** 攻击者通过覆盖栈上的返回地址，劫持 `ret` 指令的执行流。由于 `ret` 只是盲目地从栈顶取地址并跳转，攻击者可以构造一系列以 `ret` 结尾的代码片段（Gadgets），像链条一样串联起来执行任意代码。
- **防御机制：** 现代操作系统引入了 **Shadow Stack（影子栈）**、**CFI（控制流完整性）** 和 **PAC（指针认证）** 等技术，专门用于验证 `ret` 弹出的地址是否真的是由合法的 `call` 压入的。

### 5. 高级语言中的体现

虽然 C/C++/Rust 等语言中你写的是 `func()` 和 `return`，但编译器会将它们翻译为底层的 `call`/`ret` 序列，并根据**调用约定**（如 x64 System V ABI 或 Windows x64）插入额外的栈对齐、参数传递和寄存器保存/恢复代码。

> **💡 总结：** `call` 是“去且记路”，`ret` 是“原路返回”。它们是结构化编程的硬件基石，也是二进制安全和逆向工程中最基础的分析对象。

# ptr

## ptr

在汇编语言（特别是 x86/x64 的 MASM/TASM 语法）中，`ptr` 是 **Pointer** 的缩写，它是一个**类型转换/大小指定操作符**。

它的核心作用是：**明确告诉汇编器当前内存操作数的数据宽度（尺寸）**。

### 1. 为什么需要 `ptr`？

汇编器在编译时需要知道指令操作数的大小，以便生成正确的机器码。当操作数是寄存器时（如 `eax`, `al`），大小是明确的；但当操作数是**纯内存地址**且没有上下文暗示时，汇编器无法推断你要访问的是字节、字还是双字。

```nasm
; ❌ 错误：汇编器不知道要移动多少字节到内存 [ebx]
mov [ebx], 5

; ✅ 正确：使用 ptr 明确指定大小为 DWORD (4字节)
mov dword ptr [ebx], 5
```

### 2. 常见用法与尺寸对照

| 关键字      | 大小   | 对应 C/C++ 类型                  | 示例                       |
| ----------- | ------ | -------------------------------- | -------------------------- |
| `byte ptr`  | 8 bit  | `char`, `uint8_t`                | `mov byte ptr [esi], 0xFF` |
| `word ptr`  | 16 bit | `short`, `uint16_t`              | `add word ptr [ebp-4], 1`  |
| `dword ptr` | 32 bit | `int`, `float`, 指针(x86)        | `mov dword ptr [eax], ecx` |
| `qword ptr` | 64 bit | `long long`, `double`, 指针(x64) | `mov qword ptr [rsp], rax` |
| `fword ptr` | 48 bit | 远指针(16:32)                    | 极少使用                   |
| `tbyte ptr` | 80 bit | x87 FPU 扩展精度浮点             | `fld tbyte ptr [mem]`      |

### 3. 何时可以省略 `ptr`？

如果另一个操作数已经隐含了大小信息，则 `ptr` 可省略：

```nasm
; eax 是32位寄存器，汇编器自动推断 [ebx] 也是32位
mov [ebx], eax        ; ✅ 无需 dword ptr

; al 是8位寄存器，自动推断为字节操作
mov [ebx], al         ; ✅ 无需 byte ptr

; 但立即数没有固有大小，必须显式指定
mov [ebx], 0          ; ❌ 歧义
mov dword ptr [ebx], 0 ; ✅
```

### 4. ⚠️ 重要注意事项

- **`ptr` 不改变运行时行为：** 它纯粹是**汇编期（compile-time）** 的提示，不会生成任何额外指令。它只影响汇编器如何编码该条指令。
- **大小必须匹配硬件语义：** 如果你用 `word ptr` 去读一个实际只有 `byte` 有效的区域，CPU 仍会执行 16 位读取，可能导致越界访问或非预期结果。`ptr` 不做安全检查。
- NASM/GAS 语法差异：
  - **MASM/TASM:** 使用 `dword ptr [mem]`
  - **NASM:** 使用 `dword [mem]`（省略 `ptr`）
  - **GAS (AT&T):** 通过后缀表示大小，如 `movl (%ebx), %eax`（`l`=long=32bit），完全不用 `ptr`
- **与高级语言指针的区别：** 汇编中的 `ptr` **不是**一个变量或数据类型，它只是一个尺寸修饰符。不要将其等同于 C 语言中的 `*pointer` 概念。

### 5. 典型应用场景

```nasm
; 场景1：初始化局部变量
sub esp, 4
mov dword ptr [esp], 0       ; 栈上分配并初始化为0

; 场景2：字符串处理（逐字节操作）
mov byte ptr [edi], 'A'      ; 写入单个字符

; 场景3：结构体字段访问（配合偏移量）
mov eax, dword ptr [ebx+8]   ; 读取结构体偏移8处的32位成员

; 场景4：强制窄化/宽化访问（需谨慎）
mov ax, word ptr [esi]       ; 只取低16位，即使 esi 指向32位数据
```

> **记忆口诀：** "寄存器定大小，立即数靠 `ptr`；NASM 省 `ptr`，AT&T 看后缀。"

## call far ptr 标号

在 x86 汇编语言（MASM/TASM 语法）中，`call far ptr 标号` 是一条**远调用（Far Call）**指令。

与普通的近调用（Near Call）不同，它不仅改变指令指针（IP/EIP/RIP），还会**改变代码段寄存器（CS）**，从而实现跨段跳转。

### 1. 指令解析

```asm
call far ptr LabelName
```

- **`call`**: 调用指令，执行“压栈返回地址 + 跳转”操作。
- **`far ptr`**: 显式告诉汇编器这是一个**远指针**操作。它指示汇编器生成包含 **段地址:偏移地址** 的机器码，而不是仅包含偏移地址的近调用。
- **`LabelName`**: 目标函数的标号，该标号必须被定义为 `FAR` 类型（即包含段和偏移信息）。

### 2. 底层执行逻辑

当 CPU 执行 `call far ptr Label` 时，按以下顺序操作：

```text
; 伪代码描述（以16位实模式为例）
push CS          ; ① 先将当前代码段压栈
push IP          ; ② 再将当前偏移地址压栈（返回地址 = CS:IP）
CS = Label_Seg   ; ③ 加载目标段地址到 CS
IP = Label_Off   ; ④ 加载目标偏移到 IP
```

> ⚠️ **注意压栈顺序：** 远调用先压 CS 再压 IP，因此栈顶是 IP，栈顶下方是 CS。对应的 `retf` 会先弹 IP 再弹 CS。

### 3. 与 Near Call 的对比

| 特性             | `call near ptr Label` / `call Label` | `call far ptr Label` |
| ---------------- | ------------------------------------ | -------------------- |
| **跳转范围**     | 同一代码段内                         | 跨代码段             |
| **修改寄存器**   | 仅 EIP/IP                            | CS + EIP/IP          |
| **压栈内容**     | 仅返回偏移 (2/4/8字节)               | 段:偏移 (4/6/10字节) |
| **返回指令**     | `ret` (near ret)                     | `retf` (far ret)     |
| **机器码长度**   | 较短                                 | 较长（多含段选择子） |
| **现代使用频率** | 极高                                 | 极低（几乎废弃）     |

### 4. 使用场景与历史背景

#### 适用场景

- **16位实模式编程：** DOS 程序、BIOS 中断服务、多段模型（Large/Huge Memory Model）下的函数调用。
- **操作系统内核开发：** 从用户态切换到内核态（通过调用门 Call Gate），或在内核中跨段调用。
- **遗留系统维护：** 旧的 16 位 Windows/DOS 代码。

#### 现代 x86/x64 中的现状

在 **32位保护模式** 和 **64位长模式** 下，远调用几乎不再用于普通函数调用：

- **平坦内存模型（Flat Model）：** 所有代码共享同一个 CS（通常为 `0x33` 或 `0x23`），无需跨段。
- **性能惩罚：** Far call 涉及段描述符表查找、权限检查等，比 near call 慢得多。
- **64位限制：** x64 长模式下 **不支持** 传统的 `call far ptr` 直接形式进行跨段调用（只能通过间接远调用 `call far [mem]` 配合特定机制）。

### 5. 完整示例（16位 MASM）

```asm
; 定义一个 FAR 过程
MyFarProc PROC FAR
    mov ah, 09h
    int 21h
    retf                ; ← 必须用 retf，不能用 ret！
MyFarProc ENDP

; 调用方
.code
start:
    call far ptr MyFarProc   ; 远调用
    ; ...
```

### 6. ⚠️ 常见陷阱

1. **`ret` vs `retf` 不匹配：** 如果用 `call far ptr` 调用，但函数内部用了 `ret`（near ret），则只会弹出 IP，CS 不会被恢复，导致程序跳转到错误的代码段 → **崩溃**。
2. **标号未声明为 FAR：** 如果标号默认是 NEAR 类型，即使写了 `far ptr`，某些汇编器可能报错或生成错误代码。应确保过程定义为 `PROC FAR`。
3. **NASM 语法差异：** NASM 不使用 `far ptr`，而是写为 `call far Label` 或通过手动构造段:偏移来实现。
4. **保护模式下的权限：** 在保护模式下，far call 的目标段选择子必须有合法的 DPL/CPL 权限，否则触发 #GP 异常。

> 总结： `call far ptr 标号` 是 x86 分段架构的历史产物。除非你在编写 16 位程序、操作系统底层或处理特定硬件交互，否则在现代应用开发中应始终使用普通的近调用 `call Label`。
