webpack和npm不仅还有用，而且依然是前端开发的基础设施，只是角色变了：npm还是那个“包管理器”，webpack从“默认唯一选择”变成了“复杂老项目的守护者”。

### npm：依然是生态基石

npm不仅没过气，反而地位更稳了。截至2026年，npm公共注册中心托管超过200万个包，月下载量超6000亿次，仍是全球最大软件注册表。

- 市场份额：2026年Q2数据显示，npm占包管理器市场份额的58%，pnpm占28%，yarn占12%。
- 核心价值：Node.js自带npm，零配置可用；`package.json` + `package-lock.json`的依赖管理机制是所有现代前端工程的基石。
- 生态效应：即使Deno、Bun等新运行时出现，也都在做npm兼容，因为长尾场景里太多包只针对Node优化过。

> 但要注意，npm的“弃用警告”讨论主要针对旧版本架构问题，比如扁平化`node_modules`导致的幽灵依赖、安装速度瓶颈等，这些正是pnpm、yarn能抢走份额的原因。

### webpack：没死，但不再是首选

webpack 5还是2020年的产物，六年没大更新，被==Vite、Rspack、Turbopack==抢走大量新项目。 但它的真实状态是“老而不死”，甚至官方还在2026年发布了路线图。

1. 还在用：npm下载量稳居第二，大量企业级老项目深度绑定webpack的插件生态（超2万个插件），短期内不可能迁移。
2. 官方没躺平：2026年路线图明确要内置CSS Modules、TypeScript转译、HTML作为entry，还准备支持Deno和Bun，甚至参照Rspack的思路做优化。
3. 但新项目基本不选它：Vite已是新项目事实标准，2026年市场份额38%；Rspack作为“webpack继承者”，能复用90%的webpack配置，速度却快4.8倍。

> 简单说：webpack就像老牌企业系统，不会消失，但如果你在2026年新起项目，选它大概率不是最优解。

### 一个趋势

前端构建工具正在被Rust重写：Rspack、Turbopack、SWC、Rolldown（Vite 8的新核心）都是Rust写的，构建速度比webpack快一个量级。 但无论工具怎么换，npm作为交付形态依然贯穿始终——Rust工具也通过NAPI-rs生成NPM包分发。 所以npm只会越来越重要，webpack则需要看项目场景。

## ‌Rspack

[Rspack_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=Rspack)  

Rspack 是字节跳动 Web Infra 团队开发的基于 Rust 语言的高性能 Web 构建工具，截至 2026 年 8 月已发布 2.2 版本，在保持与 Webpack 生态兼容的前提下实现 10 倍左右的构建性能提升。官网：[rspack.dev](https://rspack.dev)，GitHub 仓库：[github.com/web-infra-dev/rspack](https://github.com/web-infra-dev/rspack)。

### 核心功能与 Rust 高性能特点

1. 底层架构：Rspack 使用 Rust 语言重写 Webpack 核心编译链路，包括模块扫描、AST 解析、代码转译、打包合并、产物压缩等关键环节，采用多线程全量构建模式，充分利用多核 CPU 并行能力。
2. 性能表现：
   - 冷启动提速近 7 倍，300 模块项目从 8.2 秒降至 1.1 秒。
   - 热更新达毫秒级，修改组件从 3.4 秒降至 400 毫秒。
   - 生产构建提速 6 倍，从 2 分 18 秒降至 23 秒。
   - Rspack 2.0 相较 1.0 版本最多可提升 100% 性能，2.2 版本进一步优化 HMR 和模块 ID 长度。
3. 生态兼容：高度兼容 Webpack 配置、Loader 和 Plugin，支持 babel-loader、less-loader、svgr 等常用 Loader，迁移 Webpack 老项目无需大量修改代码。
4. 内置优化：
   - 内置 SWC 工具链，转译速度是 Babel 的 20 倍。
   - 支持 Tree Shaking、代码分割、CSS 提取、模块联邦等功能，部分功能无需显式配置。
   - 2.0 版本增强静态分析能力，支持模块联邦共享依赖的 Tree Shaking。


### 与 Webpack/Vite 的对比优势

1. Webpack：
   - 优势：生态最成熟，兼容所有前端场景和第三方插件。
   - 劣势：基于 JavaScript 单线程执行，项目越大构建速度越慢，大型项目冷启动可达 30 秒以上。
   - Rspack 优势：性能是 Webpack 的 10 倍左右，配置可直接复用，迁移成本极低。
2. Vite：
   - 优势：开发环境启动快，利用浏览器原生 ESM 按需加载。
   - 劣势：生态兼容性不足，不支持 Webpack 专属 Loader/Plugin，迁移老项目成本高。
   - Rspack 优势：全场景速度快（开发/生产均优），兼容 Webpack 生态，适合存量项目提速。
3. 核心差异总结：
   - Webpack 取"兼容与生态"，舍"性能"。
   - Vite 取"性能与体验"，舍"兼容"。
   - Rspack 通过"Rust 重构 + 兼容 Webpack"实现性能、兼容、生态三重平衡。


### 适用场景与选型建议

1. 推荐使用 Rspack 的场景：
   - Webpack 老项目想提速但不想重写配置。
   - 大型企业应用，模块数超 1000+ 的大型项目。
   - CI/CD 加速场景，需要缩短生产构建时间。
   - React Native 项目，Re.Pack 5 已集成 Rspack 实现 5 倍性能提升。
2. 选型建议（2026 年生态格局）：
   - 新项目如果不是 Next.js，默认选 Vite。
   - 如果是 Next.js 项目，直接用 Turbopack。
   - 如果是存量 Webpack 项目想提速，Rspack 是性价比最高的迁移路径，对 Webpack 配置兼容度达 90% 以上。
3. 注意事项：部分 Webpack 冷门插件兼容性需验证，建议迁移前测试关键插件。

# 包管理

## 包管理属于构建工具吗

包管理不属于构建工具，两者职责不同，但常有交集。

- 包管理工具：负责下载、安装、更新、删除第三方依赖，解决“项目需要哪些库、什么版本”的问题。典型的有 `npm、yarn、pnpm、pip`
- 构建工具：负责把源代码转成可运行的产物，如编译、打包、压缩、转译。典型的有 `Webpack、Vite、Babel、Gulp`

容易混淆的点在于，不同语言生态的划分不一样：

1. JavaScript/Node.js 生态：两者基本分离。npm/yarn 管依赖，Webpack/Vite 管构建，npm scripts 只负责“调用”构建工具。
2. Java 生态：Maven 和 Gradle 既是包管理器又是构建工具，职责合一，能同时管依赖和打包。
3. Python 生态：Poetry、PDM 这类工具集依赖管理、构建、发布为一体，也属于“合体”型。

所以准确的说法是：包管理和构建是两件事，但某些工具（如 Maven、Gradle、Poetry）把两者合并了。你之前问过 Java 和 JS 构建工具的差异，这正是两个生态最大的区别——Java 喜欢“合”，JS 习惯“分”。

Java 和 JS 生态差异挺大，要不要继续看看Java 为什么倾向于合二为一?或者JS 为何习惯分离这两者?

### 后端接口规范（以Spring Boot为例）

后端不再返回HTML页面，而是通过`@RestController`暴露API，统一返回JSON结构。

```java
import org.springframework.web.bind.annotation.*;
import org.springframework.http.ResponseEntity;
import java.util.HashMap;
import java.util.Map;

@RestController
@RequestMapping("/api")
public class UserController {

    // GET请求：获取数据
    @GetMapping("/users")
    public ResponseEntity<Map<String, Object>> getUsers() {
        Map<String, Object> result = new HashMap<>();
        result.put("code", 200);
        result.put("data", List.of("User1", "User2")); // 实际应从数据库查询
        result.put("message", "success");
        return ResponseEntity.ok(result);
    }

    // POST请求：提交数据
    @PostMapping("/login")
    public ResponseEntity<Map<String, Object>> login(@RequestBody Map<String, String> body) {
        Map<String, Object> result = new HashMap<>();
        // 业务逻辑处理...
        result.put("code", 200);
        result.put("token", "xyz123");
        return ResponseEntity.ok(result);
    }
}
```

### 解决跨域问题（CORS）

前后端分离部署时，浏览器会拦截跨域请求。需在Backend配置允许跨域。

Spring Boot配置类：
```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;
import org.springframework.web.filter.CorsFilter;

@Configuration
public class CorsConfig {

    @Bean
    public CorsFilter corsFilter() {
        CorsConfiguration config = new CorsConfiguration();
        config.addAllowedOrigin("*"); // 生产环境建议指定具体域名
        config.addAllowedMethod("*");
        config.addAllowedHeader("*");
        
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return new CorsFilter(source);
    }
}
```

### SPA路由兜底（防止刷新404）

SPA前端路由（如Vue Router的History模式）由前端管理，后端需将所有非API请求重定向到`index.html`。

Spring Boot实现：
```java
import org.springframework.core.io.Resource;
import org.springframework.core.io.support.PathMatchingResourcePatternResolver;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.servlet.resource.ResourceHttpRequestHandler;

@Controller
public class SpaForwardController {

    @RequestMapping(value = "/{path:[^\\.]*}")
    public String forward() {
        // 所有不包含扩展名的路径都转发到index.html
        return "forward:/index.html";
    }
}
```
*注意：需确保`src/main/resources/static`或`templates`下有`index.html`，且静态资源路径（如/js, /css）不被此规则拦截。*

### 前端调用示例（Axios）

前端使用Axios发起异步请求，不刷新页面更新DOM。

```javascript
import axios from 'axios';

// 创建实例并配置基础URL
const api = axios.create({
  baseURL: 'http://localhost:8080/api',
  timeout: 5000
});

// 请求拦截器：自动携带Token
api.interceptors.request.use(config => {
  const token = localStorage.getItem('token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 获取用户列表
async function fetchUsers() {
  try {
    const response = await api.get('/users');
    console.log(response.data); // { code: 200, data: [...], message: "success" }
    // 更新Vue/React状态
  } catch (error) {
    console.error('请求失败:', error);
  }
}
```

### 关键坑点

1. Content-Type：POST提交JSON时，前端需设置`Content-Type: application/json`，后端用`@RequestBody`接收；若为表单提交，则用`application/x-www-form-urlencoded`，后端用`@RequestParam`或直接对象接收。
2. 404处理：若未配置路由兜底，用户在SPA子页面刷新会直接请求后端该路径，导致404。必须确保后端对非API路径返回`index.html`。
3. 接口文档：使用Swagger/OpenAPI生成在线文档，确保前后端字段定义一致。

接口规范和跨域是基础，可以继续了解RESTful设计原则或者Swagger集成方法

# 钩子函数

## vue钩子函数原理是不是类似dll

[钩子的原理](https://blog.51cto.com/linkboy/300684)  [windows钩子的编写技术](https://www.cnblogs.com/freedom831215/archive/2009/10/03/1577531.html)  

[代码注入之消息钩子注入](https://blog.csdn.net/leegh0000/article/details/147139187)  [Windows钩子函数](https://www.51cto.com/article/663626.html)  [钩子函数_百度百科](https://baike.baidu.com/item/%E9%92%A9%E5%AD%90%E5%87%BD%E6%95%B0/8722531)  

Vue 钩子函数与 DLL（动态链接库）原理不类似。两者属于完全不同的技术范畴，核心区别如下：

1.  本质不同：
    *   ==Vue 钩子==：是回调函数（Callback）机制。`Vue 框架在组件生命周期的特定阶段（如创建、挂载、更新、销毁）预留了执行点`，开发者将自定义函数“注册”到这些点上，由框架在运行时自动调用 。
    *   DLL：是二进制代码共享机制。它将编译好的函数和资源存储在独立文件中，供多个进程在运行时加载和调用，主要解决代码复用、内存节省和模块独立更新问题 。

2.  实现机制不同：
    *   Vue 钩子：基于 JavaScript 的对象属性和函数调用。Vue 内部维护一个钩子队列，在特定生命周期节点遍历并执行 `callHook` 。
    *   DLL：基于操作系统的虚拟内存映射和符号解析。通过导入表（Import Table）和导出表（Export Table）在运行时绑定函数地址 。

3.  类比误区：
    *   如果非要找相似性，==Vue 钩子更像操作系统中的中断处理或事件监听==，即在特定时刻触发预设逻辑；而 DLL 更像插件系统或共享库，提供可被调用的功能实体。

总结：Vue 钩子是软件设计模式中的“模板方法”或“观察者模式”变体，用于控制流程；DLL 是系统级的代码组织与加载方式。两者无直接原理关联。

### Windows平台的其他Hook形式

1. API Hook（API钩子）：通过修改目标程序中API函数的入口地址，劫持函数调用。通用步骤是获取API入口地址、保存原始地址、修改入口指向自定义函数。
2. IAT修改：修改PE文件输入地址表（IAT）中记录的API地址，将其指向自定义函数。当程序调用该API时，实际执行你的代码。
3. Inline Hook：直接修改函数入口处的机器码，插入跳转指令到自定义函数。比IAT修改更底层，能劫持非导出函数。
4. 注册表注入：通过修改注册表项（如AppInit_DLLs）让系统自动加载指定DLL到进程空间。
5. 远程线程注入：通过CreateRemoteThread在目标进程中创建线程，调用LoadLibrary加载指定DLL。
6. APC注入：利用线程被唤醒时APC中注册函数会执行的机制，向目标进程所有线程插入APC来执行DLL加载代码。

> 低级全局钩子（WH_KEYBOARD_LL、WH_MOUSE_LL、WH_JOURNALRECORD、WH_JOURNALPLAYBACK）是例外，它们在安装钩子的线程上下文中直接运行，不需要DLL注入。

### 编程语言层面的Hook形式

1. 回调函数：将函数作为参数传入，在特定事件发生时由主流程调用。这是最基础的Hook形式。
2. 装饰器：通过@decorator语法包装函数，在函数执行前后插入逻辑。Python中常用@register_hook形式实现声明式注册。
3. 魔术方法：实现特定方法名（如__enter__、__exit__、__len__）来钩住语言协议行为，如with语句的进入和退出时机。
4. 猴子补丁：运行时直接替换模块或类里的函数引用，改变行为。适合测试替身和临时兼容，但影响全局状态，需慎用。
5. 信号与槽：类似Qt的机制，信号发出时自动调用连接的槽函数。
6. 抽象基类：通过继承实现钩子，子类必须实现特定方法，父类在固定时机调用。
7. 上下文管理器：使用with语句的__enter__和__exit__作为钩子，管理资源获取和释放。

### 框架层面的Hook形式

1. 生命周期钩子：框架在组件创建、挂载、更新、销毁等固定时间点调用你注册的函数。如Vue的created、mounted、unmounted。
2. 路由守卫：在页面跳转前后执行的钩子，如Vue Router的beforeEach、afterEach，常用于登录鉴权。
3. 插件系统：通过注册接口或回调列表扩展核心功能，如Eclipse插件、pytest的钩子函数。
4. 测试框架钩子：pytest提供pytest_collection_modifyitems、pytest_runtest_makereport等钩子，用于测试收集、执行、报告各阶段的自定义操作。

### 各形式对比

| 实现方式            | 注册成本   | 可控性 | 适用场景             | 主要风险                 |
| ------------------- | ---------- | ------ | -------------------- | ------------------------ |
| 回调列表            | 低         | 高     | 业务扩展点、插件系统 | 需自行处理异常与顺序     |
| 装饰器注册          | 低         | 高     | 声明式注册、事件驱动 | 重复注册、忘记返回原函数 |
| 魔术方法            | 无（隐式） | 中     | 与语言结构集成       | 签名固定、调试隐晦       |
| 猴子补丁            | 低         | 低     | 测试替身、临时兼容   | 全局污染、顺序混乱       |
| API/IAT/Inline Hook | 高         | 中     | 逆向、监控、劫持     | 稳定性差、易被检测       |



钩子的本质是在某个既定流程的==特定位置预留可被外部替换或追加的入口==，核心是“控制权归属”——普通调用是“我写死了要调你”，Hook是“我预留了位置，谁来填由外部决定”。

# vue自定义事件分发

Vue 自定义事件分发核心是通过子组件调用 `$emit` 触发事件，父组件通过 `v-on` (或 `@`) 监听。Vue 3 推荐使用 `defineEmits` 显式声明事件以提供类型检查和避免原生事件冲突。

### Vue 3 (`<script setup>`) 标准写法

子组件 (Child.vue)
```vue
<template>
  <!-- 触发事件并传递参数 -->
  <button @click="handleClick">发送数据</button>
</template>

<script setup>
// 1. 定义并发出事件
const emit = defineEmits(['update-info', 'delete-item'])

const handleClick = () => {
  // 第一个参数为事件名，后续参数为 payload
  emit('update-info', { id: 1, name: 'Vue3' })
}
</script>
```

父组件 (Parent.vue)
```vue
<template>
  <!-- 2. 监听自定义事件 -->
  <Child @update-info="handleUpdate" />
</template>

<script setup>
import Child from './Child.vue'

const handleUpdate = (payload) => {
  console.log('接收到的数据:', payload) // { id: 1, name: 'Vue3' }
}
</script>
```

### Vue 2 / Options API 写法

子组件
```javascript
export default {
  methods: {
    notifyParent() {
      // 推荐事件名使用 kebab-case (短横线命名)
      this.$emit('custom-event', 'data')
    }
  }
}
```

父组件
```html
<!-- 模板中监听 -->
<child-component @custom-event="handleEvent" />

<script>
export default {
  methods: {
    handleEvent(val) {
      console.log(val)
    }
  }
}
</script>
```

### 关键注意事项

1. 事件命名：始终推荐使用 `kebab-case`（如 `my-event`），因为 HTML 属性不区分大小写，驼峰命名在 DOM 模板中可能失效 。
2. 显式声明：Vue 3 中务必使用 `emits` 选项或 `defineEmits` 声明所有自定义事件。若未声明且事件名与原生事件（如 `click`）同名，会导致事件被触发两次（一次来自 `$emit`，一次来自原生透传）。
3. 参数传递：`$emit` 第二个及之后的参数会直接传递给父组件的监听函数。若需传递多个参数，父组件监听函数可直接接收对应数量的形参，或使用 `arguments` 对象 。

事件命名和显式声明是关键，要不要继续看看事件名与原生冲突怎么避免或者显式声明事件有哪些好处

## 自定义事件分发是什么意思

[vue自定义事件分发是什么意思_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=vue%E8%87%AA%E5%AE%9A%E4%B9%89%E4%BA%8B%E4%BB%B6%E5%88%86%E5%8F%91%E6%98%AF%E4%BB%80%E4%B9%88%E6%84%8F%E6%80%9D)  

[自定义事件_百度百科](https://baike.baidu.com/item/%E8%87%AA%E5%AE%9A%E4%B9%89%E4%BA%8B%E4%BB%B6/4761096)  

Vue 自定义事件分发，简单说就是子组件通过 `$emit` 触发一个自己定义的事件，把数据“抛”出去，让父组件监听并处理。这是 Vue 里子组件向父组件传递数据的核心方式。

> 自定义事件： 由开发者定义并触发的事件，==用于实现模块间通信==，与系统内置事件不同

### 核心机制

1. 子组件触发：子组件里用 `this.$emit('事件名', 参数)` 触发自定义事件，参数就是要传给父组件的数据。
2. 父组件监听：父组件在子组件标签上用 `@事件名="处理方法"` 监听，事件触发时执行对应方法，参数自动传入。

### 代码示例

子组件：
```javascript
// 子组件 Child.vue
methods: {
  sendData() {
    // 触发 'send-toy' 事件，把 '奥特曼' 传出去
    this.$emit('send-toy', '奥特曼')
  }
}
```

父组件：
```html
<!-- 父组件 Parent.vue -->
<Child @send-toy="saveToy" />

methods: {
  saveToy(toy) {
    console.log(toy) // 输出：奥特曼
  }
}
```

### 关键注意点

- 事件名大小写：Vue 推荐用 kebab-case（短横线命名），如 `send-toy`，不要用驼峰式 `sendToy`，因为 HTML 模板会自动转小写，容易导致监听失效。
- 适用范围：`$emit` 和 `$on` 主要解决父子组件通信；兄弟组件之间不能直接用，需要通过事件总线（Event Bus）或状态管理来中转。

### 底层原理

自定义事件本质上是发布订阅模式。子组件是发布者，通过 `$emit` 发布事件；父组件是订阅者，通过 `$on` 监听。Vue 实例内部维护了事件中心，`$emit` 触发时查找并执行对应回调函数。

# VUE组合式API

## VUE组合式API是什么意思

[VUE组合式API是什么意思_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=VUE%E7%BB%84%E5%90%88%E5%BC%8FAPI%E6%98%AF%E4%BB%80%E4%B9%88%E6%84%8F%E6%80%9D)  

组合式 API（Composition API）是 Vue 提供的一种新的组件书写方式，让你可以==用函数而不是声明选项来组织代码==。它的核心意义在于：把相关的数据、方法和逻辑放在一起，而不是像 Vue 2 的选项式 API 那样，把变量塞进 `data`、函数塞进 `methods`、生命周期钩子单独放，导致同一个功能的代码被拆散到不同地方。

### 它解决了什么问题

在选项式 API 中，一个功能逻辑往往横跨多个选项块。比如一个计数器的变量在 `data` 里，对应的自增函数在 `methods` 里，等组件变大后，想改某个功能就得在文件里上下反复找，体验不太好。

组合式 API 让你按逻辑关注点来组织代码，而不是按选项类型。比如把 `count` 变量和 `increment` 函数写在一起，一眼就能看清这个功能模块的完整逻辑。

### 核心用法

1. 入口函数：用 `setup()` 或 `<script setup>` 作为组合式 API 的入口，组件创建时执行，在这里定义数据和逻辑，然后返回给模板使用。
2. 响应式状态：用 `ref()` 或 `reactive()` 创建响应式变量，值变化时视图自动更新。
3. 生命周期钩子：用 `onMounted()`、`onUnmounted()` 等函数在组件各个阶段注入逻辑。
4. 逻辑复用：可以把重复逻辑抽成自定义 Hook（普通函数），在多个组件间复用，比 Vue 2 的 mixin 更清晰、灵活。

### 一个简单的例子

```javascript
import { ref } from 'vue'

setup() {
  const count = ref(0)          // 响应式变量
  const increment = () => {     // 对应的方法，和变量放在一起
    count.value++
  }
  return { count, increment }   // 暴露给模板
}
```

### 需要注意

组合式 API 是 Vue 3 推荐的写法，但 Vue 2 也可以通过插件使用。它不改变 Vue 的核心响应式机制，只是换了一种更灵活的组织方式。官方文档对它的定位是“一系列 API 的集合”，涵盖响应式、生命周期、依赖注入等能力。

组合式 API 的核心是用函数组织代码，可以看看`它和选项式API怎么选`或者`自定义Hook怎么写`

## VUE组合式API是什么意思

Vue 的**组合式 API（Composition API）**是 Vue 3 提供的一种组织组件逻辑的新方式：把「同一个功能相关的状态和方法」集中写在一起，而不是像传统的**选项式 API（Options API）**那样按 `data`、`methods`、`computed`、`watch` 这些选项类型分散到各个区块里。

### 先看对比

**选项式 API（Vue 2 风格，Vue 3 仍支持）**

```js
export default {
  data() {
    return { count: 0, name: '' }
  },
  computed: {
    doubled() { return this.count * 2 }
  },
  methods: {
    increment() { this.count++ }
  },
  mounted() {
    console.log('mounted')
  }
}
```

逻辑按「选项类型」切分。当组件变大时，一个功能的代码会散落在 data、computed、methods、生命周期钩子等多处，来回跳跃阅读，复用也只能靠 mixins（有命名冲突、来源不清晰的问题）。

**组合式 API**

```vue
<script setup>
import { ref, computed, onMounted } from 'vue'

const count = ref(0)
const name = ref('')

const doubled = computed(() => count.value * 2)
function increment() { count.value++ }

onMounted(() => {
  console.log('mounted')
})
</script>
```

所有逻辑都是普通的变量和函数，写在同一个作用域里，相关代码天然挨在一起。

### 核心要点

- **`<script setup>`**：Vue 3.2+ 提供的语法糖，顶层的变量、函数自动暴露给模板，不用写 `export default` 和 `return`，是目前推荐的写法。
- **`ref` / `reactive`**：创建响应式数据。`ref` 用于基本值（需要 `.value` 访问），`reactive` 用于对象。
- **`computed` / `watch` / `watchEffect`**：计算属性和侦听器，变成函数调用形式。
- **生命周期钩子**：从 `mounted` 这类选项，变成 `onMounted`、`onUpdated`、`onBeforeUnmount` 等函数，可以写在任意位置、也能注册多个。
- **组合函数（Composables）**：这是组合式 API 最大的价值。把一段可复用逻辑封装成以 `use` 开头的函数，比如 `useMouse()`、`useFetch()`、`useLocalStorage()`，返回响应式状态和方法。它替代了 mixins，来源明确、可组合、支持 TypeScript 类型推导。

```js
// useMouse.js
import { ref, onMounted, onUnmounted } from 'vue'

export function useMouse() {
  const x = ref(0)
  const y = ref(0)
  const update = (e) => { x.value = e.pageX; y.value = e.pageY }

  onMounted(() => window.addEventListener('mousemove', update))
  onUnmounted(() => window.removeEventListener('mousemove', update))

  return { x, y }
}
```

组件里只需 `const { x, y } = useMouse()`。

### 为什么要有它

1. **更好的逻辑组织**：按功能聚合，而非按选项类型分散，大组件更易维护。
2. **更好的复用**：组合函数比 mixins 更清晰，没有命名冲突和隐式依赖。
3. **更友好的 TypeScript 支持**：普通函数和变量，类型推导远好于 `this` 上下文。
4. **更小的打包体积**：tree-shaking 友好，未使用的 API 可被摇掉。

### 需要注意

- 组合式 API 不是「必须换掉」的东西，选项式 API 在 Vue 3 中依然完全可用，小组件用选项式也很简洁。
- 它和 Vue 2 的 `@vue/composition-api` 插件思路一致，Vue 3 已内置。
- 在 `setup` / `<script setup>` 中不要使用 `this`，也注意 `watch` 侦听 `reactive` 对象时的深层与引用问题。

简单说：组合式 API 就是「用函数式的方式写组件逻辑」，让代码按功能组织、便于复用和类型推断，是 Vue 3 的主流写法。

2. ‌解决多重继承问题‌：在传统多重继承可能导致冲突的场景下，Mixins 提供了一种更安全的组合方式
3. ‌典型使用场景‌：
   1. 表单处理逻辑：提取跨组件的通用验证和提交逻辑
   2. 数据获取逻辑：封装异步请求、加载状态、错误处理等通用功能
   3. 日志记录功能：将日志方法混入多个组件实现统一日志管理
4. 在 Vue 框架中，Mixins 允许同时混入多个 mixin 实现功能组合，一个 mixin 可被多个组件引用

### 优缺点与最佳实践

1. 优点‌：
   1. 代码复用：避免重复实现相同逻辑
   2. 模块化：将组件拆分为功能独立的模块
   3. 灵活性：可组合多个 mixin 实现复杂功能
2. ‌缺点‌：
   1. 命名冲突：多个 mixin 可能定义同名属性或方法，导致隐式覆盖
   2. 来源模糊：难以追踪组件中某个属性的具体来源
   3. 调试困难：生命周期钩子执行顺序复杂，深层 mixin 链难以调试
3. ‌最佳实践‌：
   1. 使用命名空间隔离：如 form_validate 而非 validate，避免命名冲突
   2. 单一职责原则：一个 mixin 只处理一个功能领域
   3. 在 Vue 3 中，官方更推荐使用 Composition API 替代 Mixins，因为后者在命名冲突、类型支持、逻辑组合等方面有明显优势

mixins的优缺点里提到了命名冲突和调试困难，要不要继续看看`如何避免mixin中的命名冲突`？ 或者 `Vue3 中 Composition API 如何替代 mixins`？

# Vue的核心

## VUE操作的都是对象

[vue操作的都是对象,例如router对象_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=vue%E6%93%8D%E4%BD%9C%E7%9A%84%E9%83%BD%E6%98%AF%E5%AF%B9%E8%B1%A1%EF%BC%8C%E4%BE%8B%E5%A6%82router%E5%AF%B9%E8%B1%A1)  

对，Vue 里操作的核心确实都是对象，你提到的 router 就是典型例子。

Vue 的设计思路是“数据驱动”，你操作的对象大致分两类：

1. 响应式数据对象：`data`、`props`、`computed` 返回的对象，Vue 会通过 `Object.defineProperty`（Vue 2）或 `Proxy`（Vue 3）把它们变成响应式，改属性自动更新视图。
2. 实例与工具对象：如 `router`（路由实例）、`$route`（当前路由信息对象）、`$refs`、组件实例 `this` 本身，都是对象，承载方法或状态供调用。

### 路由相关的两个对象

- `$router`：路由操作对象，负责跳转，`$router.push()`、`$router.replace()` 都是方法调用，只写对象。
- `$route`：路由信息对象，只读，存当前 URL 解析结果，如 `path`、`params`、`query`、`hash`、`matched` 等。

每次导航成功，`$route` 会生成新对象并被 `Object.freeze` 冻结，所以不能直接改，只能通过 `$router` 跳转来变。

### 操作对象时注意

- 新增属性：Vue 2 无法检测对象新增属性，需用 `this.$set(obj, key, value)` 才能触发视图更新；Vue 3 用 Proxy 没这限制。
- 直接赋值：已有属性直接赋值没问题，如 `this.user.name = '新值'` 会触发更新。
- 不要改 `$route`：它被冻结，改了无效，想跳转用 `router.push`。

一句话总结：==Vue 里你写的、调用的、传的基本都是对象==，理解“哪些是响应式数据、哪些是工具实例、哪些只读”是用的关键。

## Vue 的设计思路是数据驱动

对，这句话抓住了 Vue 的核心。更完整一点表述是：**用声明式的方式描述「界面 = 数据的函数」，数据变化时框架自动更新界面**，开发者不再手动去改 DOM。

### 数据驱动具体体现在哪

**1. 声明式渲染，而非命令式操作**

jQuery 时代的思维是「找到节点 → 改它」：

```js
$('#count').text(0)
$('#btn').on('click', () => {
  const n = Number($('#count').text()) + 1
  $('#count').text(n)
})
```

Vue 里你只声明「界面长什么样」，至于怎么变，是框架的事：

```vue
<span>{{ count }}</span>
<button @click="count++">+1</button>
```

**2. 响应式系统是引擎**

数据被 `ref` / `reactive` 包装后会被追踪依赖，数据一变，对应的渲染 effect 重新执行，产生新的虚拟 DOM，再 diff 出最小补丁更新真实 DOM。Vue 3 用 `Proxy` 做拦截，所以能感知新增/删除属性，粒度也更细（一个组件一个 effect，而非全局脏检查）。

**3. 单向数据流**

数据从父组件通过 props 往下流，子组件用 emit 往上通知。这条约束让「数据从哪来」始终可追溯，是数据驱动能维持可维护性的前提。Pinia / Vuex 则是把这条思路推到全局：单一数据源 + 显式修改。

### 几个容易误解的点

- **数据驱动 ≠ 数据一变就整棵树重渲染。** 依赖收集决定了只有真正用到该数据的组件才会更新，diff 又进一步缩小 DOM 操作范围。
- **数据驱动 ≠ 不能碰 DOM。** 需要聚焦、滚动、集成第三方库时，模板 ref 和 `nextTick` 依然是正当手段，只是应作为例外而非常态。
- **交互仍是事件驱动。** 数据驱动解决的是「视图如何随状态变化」，用户输入、定时器、网络请求这些副作用仍需你显式编写，这也是为什么会有生命周期钩子和 `watch`。
- **状态要「可预测」才算真正受益。** 如果为了绕过响应式而到处 `JSON.parse(JSON.stringify())`、或者在组件外偷偷改对象，数据驱动的收益就打折了。

### 和上一轮聊的组合式 API 什么关系

两者是不同层面的事：

- **数据驱动**是 Vue 的底层渲染理念，从 Vue 1 到现在没变过。
- **组合式 API**改变的是「你如何组织操作这些数据的逻辑」——把相关的响应式状态和方法聚到一起、便于复用。

可以说 `ref` / `reactive` / `computed` 正是数据驱动在组合式 API 里的入口：组合函数返回的响应式状态，依然是驱动视图更新的那份数据。所以学了组合式 API，数据驱动这套心智模型完全不用推翻。

Vue 路由组件传参主要有三种方式：动态路由参数（params）、查询字符串（query）和 props 解耦传参。 核心区别在于参数放哪里、刷新后是否保留、以及组件是否依赖 `$route`。

### 三种方式对比

1. 动态路由参数（params）：参数嵌在路径里，如 `/user/123`。适合传单个必填的资源标识，如用户 ID、商品 ID。
   - 传参：`this.$router.push({ name: 'User', params: { id: 123 } })` 或 `this.$router.push('/user/123')` 
   - 接收：`this.$route.params.id` 
   - 注意：路由定义需提前声明 `path: '/user/:id'`；用对象写法传 params 时必须用 `name` 跳转，不能用 `path`。

2. 查询字符串（query）：参数拼在 URL 问号后面，如 `/search?keyword=vue&page=2`。适合传多个筛选条件、搜索关键词、分页参数。
   - 传参：`this.$router.push({ path: '/search', query: { keyword: 'vue', page: 2 } })` 
   - 接收：`this.$route.query.keyword` 
   - 优点：刷新页面参数不丢失，因为数据就在地址栏里。

3. props 解耦传参：在路由配置里开 `props`，让路由参数直接作为组件属性传入，组件内不再需要写 `$route`。
   - 布尔模式：`props: true` 时，`route.params` 自动映射为组件 props。
   - 对象模式：`props: { newsletterPopup: false }`，适合传静态值。
   - 函数模式：`props: route => ({ query: route.query.q })`，灵活转换参数。
   - 优点：组件与路由解耦，复用性和可测试性更好，是官方推荐写法。

### 怎么选

| 场景                 | 推荐方式                    |
| -------------------- | --------------------------- |
| 详情页传 ID          | params 动态路由             |
| 列表筛选、分页、搜索 | query 查询参数              |
| 组件复用、解耦路由   | props 传参                  |
| 临时敏感数据         | history.state 或 Pinia/Vuex |

### Vue2 和 Vue3 的区别

- Vue3 中用 `useRoute()` 和 `useRouter()` 替代 `this.$route` 和 `this.$router`。
- Vue Router 4 移除了“隐式 params 传参”——如果路由没定义 `:id` 占位符，用 params 传参刷新后会丢失，必须改用 query、动态路由或 state。
- Vue Router 4 新增了 `history.state` 传参，数据不显示在 URL 上。

### 小提示

- 用 params 传参时，如果路由没定义对应动态段，刷新页面参数会丢；query 不会丢。
- 同一个组件在不同路由间复用，参数变化时记得用 `watch` 监听 `$route` 或 `useRoute()`，否则页面可能不更新。

三种传参方式各有适用场景，可以看看params传参刷新丢失的原因或者query参数拼接的规则

## 什么是vue状态管理

Vue状态管理就是集中管理应用中==所有组件共享数据==的一种模式，核心目的是让组件间的数据共享更清晰、可预测，避免“谁改了数据”说不清。

简单说，`当多个组件需要共享同一份数据`（如用户登录信息、购物车商品），`把这份数据从组件里抽出来，放到一个全局的“仓库”里统一管理`，任何组件都能读取或修改，且修改规则固定，方便调试和追踪。

### 为什么需要它

Vue本身是单向数据流，组件传props层层传递，兄弟组件共享状态很麻烦，代码易乱且难维护。把共享状态抽成全局单例，组件树里任何位置都能获取状态或触发行为，代码更结构化。

### 核心概念

1. State：单一状态树，存放所有共享数据，是唯一数据源，响应式，变了视图自动更新。
2. Mutations：同步修改State的唯一途径，通过`commit`提交，每个改动都留下记录，方便追踪。
3. Actions：处理异步操作（如网络请求），提交Mutation而非直接改状态。
4. Getters：类似计算属性，从State派生数据，可复用。
5. Modules：项目大时把Store拆成模块，每个模块有自己的State、Mutations等。

> 不能直接修改`store.state`里的数据，必须通过Mutation，否则调试工具无法追踪变化，严格模式下还会报错。

### Vuex vs Pinia

Vue 3项目现在==更推荐用Pinia==，它更轻量、API更简洁，天然支持组合式API写法，Vuex 4虽可用但官方已把Pinia作为默认推荐。 Vue 2配Vuex 3，Vue 3配Vuex 4或Pinia，版本别搞混。

Pinia确实更轻量，要不要看看Pinia和Vuex的核心区别或者Pinia的模块化用法

# 服务端渲染

## 服务端渲染

[服务端渲染_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=%E6%9C%8D%E5%8A%A1%E7%AB%AF%E6%B8%B2%E6%9F%93)  

服务端渲染（SSR）就是在服务器上把网页内容拼好，直接发给浏览器显示，用户打开页面时不用等大量 JavaScript 加载完就能看到内容。它适合对首屏速度和搜索引擎收录要求较高的网站，比如新闻、博客、电商首页等。

### 服务端是怎么把页面“拼”出来的

1. 浏览器发起请求：用户在地址栏输入网址或点击链接，向服务器要页面。
2. 服务器处理数据：服务器收到请求后，查询数据库或调用接口，把页面需要的数据准备好。
3. 生成完整 HTML：服务器用框架或模板引擎把组件和数据拼成一个完整的 HTML 页面。
4. 返回给浏览器：服务器把渲染好的 HTML 一次性发回，浏览器拿到后可立即展示。
5. 客户端“激活”交互：页面显示后，浏览器再加载 JavaScript，把页面上的按钮、表单等交互功能接上，这个过程也叫“水合”。


### 和客户端渲染比，SSR 有什么不同

1. 页面谁来生成
   - SSR：服务器生成完整 HTML，浏览器直接显示。
   - 客户端渲染（CSR）：浏览器先拿到空白 HTML 和脚本，再由 JavaScript 生成页面内容。
2. 首屏速度
   - SSR：更快，因为 HTML 已经包含内容，不用等 JS 执行完。
   - CSR：较慢，需要先下载、执行 JS，再请求数据并渲染。
3. 搜索引擎收录
   - SSR：更好，爬虫可以直接读取到页面内容。
   - CSR：相对较弱，需要额外做预渲染或 SSR 支持才能让爬虫抓到内容。
4. 服务器压力
   - SSR：更高，每次请求都要在服务器上渲染页面。
   - CSR：更低，服务器主要提供接口和静态文件。
5. 开发复杂度
   - SSR：较高，需要前后端配合，代码要能在服务器和浏览器两端运行。
   - CSR：较低，前后端分离更彻底，前端独立开发更方便。


### 哪些项目更适合用服务端渲染

1. 内容展示型网站：如新闻、博客、文档站，用户更关心快速看到内容。
2. 对 SEO 要求高的业务：如电商商品页、营销落地页，需要被搜索引擎更好地收录。
3. 首屏加载体验优先：网络条件一般或低端设备较多时，SSR 能减少白屏等待。
4. 不太适合的场景：管理后台、强交互应用、前后端团队分离较彻底的项目，通常用 CSR 更灵活。




常见实现 SSR 的框架有 Next.js（React）、Nuxt.js（Vue）、Angular Universal（Angular）等，早期 PHP、JSP 也采用过类似思路。

## 服务端渲染要在服务器上设置吗

[服务端渲染要在服务器上设置吗_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=%E6%9C%8D%E5%8A%A1%E7%AB%AF%E6%B8%B2%E6%9F%93%E8%A6%81%E5%9C%A8%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%8A%E8%AE%BE%E7%BD%AE%E5%90%97)  

是的，服务端渲染（SSR）必须在服务器上设置和运行，它本质上就是“在服务器端完成页面HTML组装”的渲染模式，和纯静态部署的客户端渲染（CSR）完全不同。

### 为什么必须要在服务器上配置

SSR的核心逻辑是：服务器接收请求 → 在服务端把组件渲染成完整HTML → 返回给浏览器。这意味着服务器上必须有一个能执行渲染逻辑的Web服务进程（比如Node.js），而不是只放静态文件。

- 运行环境：服务器需要安装对应运行时（如Node.js），并启动Web服务器（Express、Koa等）来监听请求、执行渲染逻辑。
- 构建产物不同：SSR项目需构建出服务端bundle（如`vue-ssr-server-bundle.json`）和客户端manifest，部署时要把这些产物连同服务端入口文件一起上传，再在服务器上启动服务。
- 部署方式不同：CSR只需把静态文件放到CDN或Nginx即可；SSR则需在服务器上常驻一个Node进程，通常用PM2等工具来维护，实现异常重启、端口复用等。

### 具体要配置什么

1. 服务端入口：创建`entry-server.js`，导出一个接收请求上下文、返回应用实例的函数，服务器用它来渲染每个请求。
2. 服务器代码：写一个`server.js`，用Express或Koa处理路由，调用渲染函数生成HTML并返回。
3. 构建配置：Webpack或Vite需分别打包客户端和服务端代码，服务端构建要设置`target: 'node'`，并排除第三方依赖。
4. 静态资源：客户端构建产物（JS/CSS等）需在服务器上通过静态文件服务暴露出来，供浏览器加载。

### 不想手动搭？用框架

若不想从零配置，可选用Next.js（React）或Nuxt（Vue），它们内置SSR能力，默认在服务器端渲染页面，你只需写业务代码，框架帮你处理构建和服务器逻辑。

> 注意：SSR会增加服务器压力，因为每次请求都要动态生成HTML。若页面内容偏静态，可结合缓存策略（如LRU缓存）减轻负担。

SSR确实需要服务器配置，想了解具体怎么操作的话，可以看看Next.js和Nuxt的SSR配置区别或者SSR缓存策略有哪些常见类型
