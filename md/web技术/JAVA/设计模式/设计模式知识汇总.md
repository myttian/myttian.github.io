## java设计模式的产生原因

[java设计模式的产生原因_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=java%E8%AE%BE%E8%AE%A1%E6%A8%A1%E5%BC%8F%E7%9A%84%E4%BA%A7%E7%94%9F%E5%8E%9F%E5%9B%A0)  

设计模式产生的根本原因是==为了解决软件开发中反复出现的特定问题，提供经过验证的、可复用的解决方案==，以应对软件系统的复杂性、变化性和维护成本。

1. 解决重复性问题与经验传承
软件开发中存在大量普遍且重复出现的问题（如对象创建、接口兼容、状态管理等）。设计模式是对这些问题的标准化解决方案总结，避免了“重复造轮子”，将优秀的设计经验固化下来，供开发者直接复用。

2. 应对软件复杂性与解耦
随着业务逻辑复杂化，代码容易陷入紧耦合、高内聚的困境。设计模式通过特定的结构（如依赖倒置、接口隔离）降低模块间的耦合度，使系统结构更清晰，便于理解和维护。

3. 提高可扩展性与可维护性（开闭原则）
需求变更是常态。设计模式旨在实现“对扩展开放，对修改关闭”。通过抽象和多态，使得在增加新功能时无需修改原有代码，从而降低引入Bug的风险，提升系统的灵活性和稳定性。

4. 统一沟通语言
设计模式为开发团队提供了一套通用的术语和思维框架。使用“单例”、“观察者”等词汇能高效传达设计意图，减少沟通成本，促进团队协作。

5. 历史渊源
概念源于建筑学家 Christopher Alexander 的《建筑模式语言》，后由 GoF（四人组）在 1995 年出版的《设计模式：可复用面向对象软件的基础》中引入软件工程领域，确立了 23 种经典模式。

设计模式的根源在建筑学，要不要了解一下《建筑模式语言》的核心思想或者GoF四人组的成员背景

## 静态代理和动态代理

[静态代理和动态代理对比_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=%E9%9D%99%E6%80%81%E4%BB%A3%E7%90%86%E5%92%8C%E5%8A%A8%E6%80%81%E4%BB%A3%E7%90%86%E5%AF%B9%E6%AF%94)  

静态代理在编译期就确定代理类，动态代理则在运行时动态生成代理类，这是两者最核心的分界线。静态代理需要你为每个目标类手写一个代理类，而动态代理通过反射机制在内存中统一生成，代码量大幅减少。

### 核心区别

1. 代理类生成时机：静态代理的 `.class` 文件在编译时已存在；动态代理的字节码在程序运行中由 JVM 动态生成，只存在于内存，不落盘。

2. 代码量：静态代理要为每个被代理类单独写代理类，接口新增方法时目标类和代理类都要改；动态代理一个处理器即可服务多个目标类，无需逐个修改。

3. 灵活性：动态代理更灵活，不需要针对每个目标类都创建代理类，且能统一处理所有代理方法的增强逻辑。

### 动态代理的两种实现

1. JDK 动态代理：基于接口，通过 `Proxy.newProxyInstance()` 生成代理类，要求目标类必须实现接口，只能代理接口中声明的方法。

2. CGLIB 动态代理：基于继承，通过字节码技术生成目标类的子类，不要求实现接口，但目标类不能是 `final` 的。

> Spring AOP 的默认策略是：目标类实现了接口就用 JDK 动态代理，否则用 CGLIB。

### 静态代理的局限

静态代理在接口新增方法时，目标对象和代理对象都要同步修改，维护成本高；目标类一多，代理类数量膨胀，代码冗余明显。这些缺陷正是动态代理诞生的原因。

动态代理的实现方式各有特点，可以看看JDK动态代理和CGLIB代理的原理区别或者Spring AOP为什么默认用JDK代理?
