  - ==建本地版本库==：先建目录，`git init`把目录变成git可管理的仓库。  `.git`目录是Git跟踪管理版本库的

    - ==提交新文件2步==：文件添加到仓库： `git add read.txt`  ;    文件提交到仓库：`git commit -m "提交"`  

  - ==时光机穿梭==

    - ==提交修改==和提交新文件是一样的两步add\commit： `git status`查看文件改变；  `git diff me.text`查看修改内容（工作区和版本库里的区别）；  
    - ==版本回退==：`git log  --pretty=oneline` 提交日志，一大串是版本号；`HEAD`表示当前版本 ; 上一个版本`HEAD^` ; 上100个`HEAD~100`  ；回退：`git reset --hard HEAD^` ； 返回回退前的版本：`git reset --hard 1094a` ，要写版本号；   找不到版本号用``git reflog`
    - 工作区和暂存区：`.git`是版本库，里面stage（或者叫index）是暂存区； 例如： <span style=color:red>add把文件从工作区添加到暂存区；commit把暂存区内容提交到当前分支；</span>   g
    - 管理修改： Git跟踪并管理的是修改，而非文件；  每次修改，如果不用`git add`到暂存区，就不会加入到`commit`中
    - ==撤销修改==：`git checkout --  readme.txt` ; 2种情况：1、改后没到暂存区，回版本库；2、加到暂存区后又作了修改，回加到暂存区状态。   修改回到 最近一次` add` 或 `commit` 状态 ；  没有`--`，就变成了“切换到另一个分支” ；
      `git reset HEAD readme.txt`  既可以回退版本，也可以把<span style=color:red>暂存区修改回退到工作区</span>
      <span style=color:red>reset清空暂存区修改；   checkout清空工作区修改</span>
    - 删除文件：删除也是一个修改操作, `git rm  test.txt` 删掉，并且`git commit`； 

  - ==分支管理==

    - 在分支上干活， 开发完毕后，再一次性合并到原来的分支上，既安全，又不影响别人工作；   `创建、切换和删除分支`

    - ==创建与合并==：<span style=color:red>创建分支</span>：增加一个dev分支指针，让`HEAD`指向这个指针。 <span style=color:red>合并分支</span>： 直接把`master`指向`dev`的当前提交  (master指向dev，head指向master) 。 <span style=color:red>删分支</span>： 删分支指针就行了。

      ```ts
      //创建dev分支，然后切换到dev分支
      git checkout -b dev   //-b表示创建并切换
      //git branch查看当前分支
      
      //分支工作完成，切换回master
      git checkout master    //新版git用 git switch -c dev  切换分支
      //把dev合并到master分支
      git merge dev     //合并指定分支到当前分支;    这种是快进模式合并分支，合并很快
      //合并完成后，就可以放心地删除dev分支
      git branch -d dev	
      git branch -r查看远程分支
      git branch -a：查看本地和远程仓库的所有分支
      git checkout 远程分支名：拉取远程分支并同时创建对应的本地分支
      ```

      > 查看分支：`git branch`
      >
      > 创建分支：`git branch <name>`
      >
      > 切换分支：`git checkout <name>`或者`git switch <name>`
      >
      > 创建+切换分支：`git checkout -b <name>`或者`git switch -c <name>`
      >
      > 合并某分支到当前分支：`git merge <name>`
      >
      > 删除分支：`git branch -d <name>`
      >
      > 改名：`git branch -m <old> <new>`

    - ==解决冲突==：无法自动合并分支时，首先解决冲突。再提交，合并完成 ；  解决冲突就是把Git合并失败的文件手动编辑为我们希望的内容，再提交；  `git log --graph`看分支合并图   `git log --graph --pretty=oneline --abbrev-commit`  abbrev缩写

    - ==分支管理策略==：通常，合并分支用`Fast forward`模式，但这种模式下，删除分支后，会丢掉分支信息;  强制禁用`Fast forward`模式，Git就会在merge时**生成一个新的commit**，这样，从分支历史上就可以看出分支信息。   `--no-ff`方式的`git merge`  ， `git merge --no-ff -m "merge with no-ff" dev`   ；  
      实际开发中：每个人都有自己的分支，时不时地往`dev`分支上合并，发布时，再把`dev`分支合并到`master`上 。

    - ==bug分支==：Git提供了一个`stash`功能，可以把当前工作现场“储藏”起来，等以后恢复现场后继续工作  。`git stash`    `git stash list`  ；恢复封存区2种方法： `git stash apply`恢复，恢复后，stash内容并不删除，要用`git stash drop`来删除 ； 2是用`git stash pop`，恢复的同时把stash内容也删了

      <span style=color:red>`git stash`封存dev分支工作现场 >> 在bug分支创建临时分支，修复bug ，然后临时分支合并到bug分支，删临时 >> 回到dev，恢复工作现场 `git stash pop`</span>

      ==复制一个提交到当前分支==： dev分支是早期从master分支分出来的，bug其实在当前dev分支上也存在； 在master分支上修复的bug，想要合并到当前dev分支，可以用`git cherry-pick <commit>`命令，把bug提交的修改“复制”到当前分支，避免重复劳动。

    - ==feature分支==：软件开发中，总有新功能要不断添加进来，每添加一个新功能，最好新建一个feature分支，在上面开发，完成后，合并，最后，删除该feature分支
      因经费不足，新功能必须取消！虽然白干了，但是这个包含机密资料的分支还是必须就地销毁   ； 要丢弃一个没有被合并过的分支，可以通过`git branch -D <name>`强行删除;  `git branch --delete --remotes dev`删除追踪分支  `git push origin -d dev`删远程分支

    - ==多人协作==：`git remote -v`查看远程库；  `git checkout -b dev origin/dev`  创建远程的`dev`分支到本地；   **push到远程冲突**：先``git pull`把最新的提交从`origin/dev`抓下来， 在本地合并，解决冲突，再推送；   没有指定本地`dev`分支与远程`origin/dev`分支的链接 ：`git branch --set-upstream-to=origin/dev dev`

      ```ts
      //多人协作的工作模式
      1、首先，可以试图用git push origin <branch-name>推送自己的修改；
      2、如果推送失败，则因为远程分支比你的本地更新，需要先用git pull试图合并；
      3、如果合并有冲突，则解决冲突，并在本地提交；
      4、没有冲突或者解决掉冲突后，再用git push origin <branch-name>推送就能成功！
      ```

      

    - ==Rebase==：把分叉的提交历史“整理”成一条直线；把本地未push的分叉提交历史整理成直线； 目的是使得我们在查看历史提交的变化时更容易，因为分叉的提交需要三方对比  `git rebase`

  - ==标签管理==

    - 创建标签：发布一个版本时，通常先在版本库中打一个标签（tag），就唯一确定了打标签时刻的版本。将来取某个标签的版本，就是把那个打标签的时刻的历史版本取出来。所以，标签也是版本库的一个快照。***标签：指向某个commit的指针*** , tag是一个让人容易记住的有意义的名字，它跟某个commit号（6a5819e...）绑在一起


# 对比



Docsify的核心优势是“零构建、纯前端即时渲染”，只需一个`index.html`加一堆Markdown文件，浏览器访问时动态加载渲染，无需编译打包，改完刷新即生效。

### 它和其他工具的核心区别

1. 与GitBook比：GitBook是商业化平台，可定制性差，对中文支持一般；Docsify完全开源免费，更轻更自由。
2. 与VuePress/VitePress比：VuePress在编译期预渲染HTML，SEO友好、定制能力强，但配置复杂，每次修改需重新构建；Docsify上手极快，但首屏白屏时间稍长，SEO不友好。
3. 与Hexo比：Hexo本质是博客引擎，做文档导航不顺手；Docsify天生为文档设计，侧边栏、目录、搜索即开即用。
4. 与Docute比：两者理念几乎一样，但Docute基于Vue生态，体积约60kB，是Docsify（约20kB）的3倍；Docsify用原生JS实现，更轻量。

### 性能对比（同环境下测试数据）

| 指标           | Docsify | GitBook | Hexo  | VuePress |
| -------------- | ------- | ------- | ----- | -------- |
| 初始加载时间   | 120ms   | 850ms   | 320ms | 680ms    |
| 首次内容绘制   | 180ms   | 920ms   | 410ms | 750ms    |
| 文档体积(gzip) | 15KB    | 82KB    | 45KB  | 68KB     |
| 100页构建时间  | 0s      | 45s     | 18s   | 32s      |

数据来源：2023年文档工具性能基准测试报告。

### 什么时候选Docsify

- 快速搭建：内部项目手册、开源项目文档、轻量知识库，5分钟跑通。
- 内容更新频繁：改完Markdown刷新即见效果，无“改完忘了build”的心理负担。
- 协作门槛低：贡献者只需会Markdown，加个文件加行链接即可，不要求懂前端构建。
- 追求极简部署：整个站点就一个HTML加一堆.md，扔到任何静态服务器都能跑。

### 什么时候不选Docsify

- 需要SEO：完全客户端渲染，搜索引擎爬不到内容，对外公开文档要流量就不合适。
- 需要复杂交互定制：想在Markdown里嵌入Vue组件、深度定制主题，VuePress更合适。
- 文档层级非常深：搜索插件在目录层级超4层时可能卡死，需手动配置`depth`限制递归深度。

> 一句话总结：Docsify适合“内容为主、快速维护、不追求SEO”的内部文档场景；大型公开文档站或需深度定制，VuePress更值得投入。

你之前看微服务架构时，如果想把学习笔记整理成可浏览的文档站，Docsify确实是最省心的选择，不用折腾构建工具链。

Docsify的轻量和易用是它的核心，要不要继续看看它支持哪些版本控制或者如何实现文档搜索功能

文档服务器主要分传统文件服务器、云文档平台和开源自建方案三大类，具体选择看规模、安全要求和预算。

### 传统文件服务器

适合需要本地化部署、数据不出内网的企业。

- Windows Server：最常用的企业文件服务器系统，支持AD域集成，权限管理方便。
- Linux/NFS + Samba：NFS适合Linux/Unix环境，Samba能让Linux和Windows无缝对接。
- NAS设备：如TrueNAS、群晖等，即插即用，支持RAID，适合中小企业私有云。
- CuteHttpFileServer (chfs)：开源轻量HTTP文件共享服务器，单文件运行，跨平台支持，适合快速搭建临时共享。

### 云文档与协同平台

适合需要多人协作、远程访问、权限精细管控的团队。

- 亿方云：360旗下企业级网盘，主打大容量存储、在线编辑、安全合规，支持私有化部署，适合中大型企业。
- PingCode 知识库：国产知识管理头部产品，适合研发团队，支持与需求、测试、缺陷打通，25人以下免费。
- 石墨文档：在线协作Office，多人实时编辑体验流畅，支持私有化部署。
- 语雀：蚂蚁集团出品，结构化知识库管理，适合技术文档沉淀和团队规范管理。
- Worktile：项目协作与文件管理结合，适合让文件跟随项目流程流转的团队。
- 坚果云：轻量稳定企业云盘，文件同步和版本控制是强项。
- 微软SharePoint + OneDrive：适合深度使用Microsoft 365生态的企业，与Office文档协作无缝结合。
- Google Drive for Workspace：适合海外或跨境团队，在线协作体验好。
- 腾讯文档、金山文档、WPS云文档：国内常用，与微信、WPS生态融合深，适合日常办公协作。

### 开源自建方案

适合有技术团队、数据自主可控要求高的组织。

- Nextcloud：开源==自托管==文件协作平台，支持插件扩展，适合有运维能力的企业。
- Seafile 企业版：私有化文件同步效率高，适合替代传统共享盘。
- DokuWiki：轻量开源Wiki，无需数据库，数据存为文本文件，适合搭建内部知识库。
- MrDoc：基于Python的轻量开源知识库，支持私有化部署，适合个人或中小团队。
- OnlyOffice：开源Office套件，高度兼容MS Office格式，可私有化部署在线编辑。
- OpenKM、SeedDMS、OpenDocMan：开源文档管理系统（DMS），功能从企业级到轻量级都有。

> 选型关键：传统文件服务器适合数据敏感、本地化部署需求强的企业；云文档平台适合协作效率要求高、远程办公多的团队；开源自建适合有技术能力、预算有限但要求数据自主可控的组织。

选型时除了看类型，还可以了解传统服务器和云平台哪个更安全或者开源方案和商业平台成本差多少
