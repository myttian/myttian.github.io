Linux可执行文件用的是ELF（Executable and Linkable Format，可执行与可链接格式）结构，这也是Linux系统中最标准的二进制文件格式。

### 整体组成

一个ELF文件通常由四部分组成：

1. ELF头（ELF Header）：文件起点，操作系统加载时最先读取。包含魔数（前4字节 `7f 45 4c 46`，即 `\x7fELF`）、文件类型、目标架构、入口地址等信息。
2. 程序头表（Program Header Table）：描述段（Segment）如何映射到内存，加载器依据此表完成加载，可执行文件必须包含。
3. 节（Sections）：存放代码、数据、符号表等实际内容，如 `.text`（代码）、`.data`（已初始化数据）、`.bss`（未初始化数据）、`.rodata`（只读数据）。
4. 节头表（Section Header Table）：描述每个节的位置、大小、类型等信息，主要用于链接和调试。

### 两种视图

ELF核心设计是“一文件两套视角”：

- 链接视图：从链接器角度看，以节（Section）为单位，关注符号表、重定位信息等。
- 执行视图：从操作系统加载器角度看，以段（Segment）为单位，关注权限、对齐、入口地址等。

多个属性相近的节会被合并成一个段，以满足内存页（通常4KB）对齐要求。

### 常见节类型

| 节名      | 存放内容                | 权限    |
| --------- | ----------------------- | ------- |
| `.text`   | 可执行代码              | 读+执行 |
| `.data`   | 已初始化的全局/静态变量 | 读+写   |
| `.bss`    | 未初始化的全局/静态变量 | 读+写   |
| `.rodata` | 字符串常量、只读数据    | 只读    |

### 查看方法

可用以下命令查看ELF文件内部结构：

- `readelf -h 文件名`：查看ELF头
- `readelf -l 文件名`：查看程序头表（段信息）
- `readelf -S 文件名`：查看节头表
- `objdump -d 文件名`：反汇编代码段

另外，Linux不靠扩展名识别可执行文件，而是看文件内容和执行权限，与Windows的 `.exe` 机制不同。

## ELF结构

ELF（Executable and Linkable Format）是Linux等类Unix系统的主要可执行文件格式，用于描述可执行文件、目标代码、共享库和核心转储文件。

### 📁 整体组成

一个ELF文件由四部分组成：

1. ELF头（ELF Header）：位于文件开头，是固定位置，描述文件类型、目标架构、入口地址等基本信息，并定位其他部分的位置。
2. 程序头表（Program Header Table）：描述段（Segment）在内存中的布局，供操作系统加载程序时使用。
3. 节（Sections）：存放代码、数据、符号表等实际内容，是链接视图的基本组织单位。
4. 节头表（Section Header Table）：描述每个节的名称、类型、位置、大小等属性，用于链接和调试。

### 👀 两种视图

- 链接视图（Linking View）：从链接器角度看，文件由一个个节（Section）组成，如`.text`、`.data`、`.bss`，粒度细，便于符号解析和重定位。
- 执行视图（Execution View）：从操作系统加载器角度看，文件由一个个段（Segment）组成，一个段包含一个或多个节，按页对齐合并，便于内存映射。

### 📋 ELF头关键字段

ELF头是文件起点，操作系统加载时第一个读取它。

| 字段        | 含义                                                         |
| ----------- | ------------------------------------------------------------ |
| `e_ident`   | 16字节标识数组，前4字节为魔术值 `0x7F 'E' 'L' 'F'`，任何ELF文件必须以此开头 |
| `e_type`    | 文件类型：`ET_REL`（可重定位）、`ET_EXEC`（可执行）、`ET_DYN`（共享库）等 |
| `e_machine` | 目标架构，如 `0x3E` 对应 x86-64                              |
| `e_entry`   | 程序入口点虚拟地址，即第一条指令执行位置                     |
| `e_phoff`   | 程序头表在文件中的偏移                                       |
| `e_shoff`   | 节头表在文件中的偏移                                         |

### 🔍 常见节

- `.text`：可执行代码，只读、可执行权限（r-x）
- `.rodata`：只读数据，如字符串常量、const全局变量（r--）
- `.data`：已初始化的全局/静态变量，在文件和内存中都占空间（rw-）
- `.bss`：未初始化或全零的全局/静态变量，不占文件空间，启动时清零（rw-）
- `.symtab`：符号表，记录函数和变量的定义与引用
- `.strtab`：字符串表，存储符号名称

> 节与段易混淆：节给链接器看，段给内核看。内核加载ELF时只遍历程序头表，找`PT_LOAD`类型的段，用`mmap`映射到内存，不关心节。

### 🛠️ 查看工具

- `readelf -h`：查看ELF头
- `readelf -S`：查看节头表
- `readelf -l`：查看程序头表（段信息）
- `objdump -d`：反汇编代码
- `objdump -t`：查看符号表

### 🔄 加载流程

1. 内核读取ELF头，验证魔术值确认格式合法
2. 根据`e_phoff`定位程序头表，遍历`PT_LOAD`段
3. 将各段通过`mmap`映射到进程虚拟地址空间，按段flags设置权限
4. 跳转到`e_entry`指定的入口地址开始执行，实际入口通常是`_start`而非`main`

结合你之前查的中断、BIOS等底层知识，ELF结构正是连接编译产物和操作系统加载机制的桥梁，理解它有助于看清程序从磁盘到内存执行的完整链路。

## pe文件框架

PE文件框架就是Windows下可执行文件的整体结构，从DOS头到节表再到节区，层层嵌套。它像容器，头部记录元信息，节表充当目录索引，节区存放真实代码和数据。

### 整体分层结构

PE文件按顺序排列，加载时系统按偏移定位：

1. DOS头（IMAGE_DOS_HEADER）：文件最开头64字节，以“MZ”标志（0x5A4D）起始，用于DOS兼容。关键字段是偏移0x3C处的`e_lfanew`，指向PE头起始位置。
2. DOS存根（DOS Stub）：DOS下运行的程序，通常显示“This program cannot be run in DOS mode”提示。
3. PE签名（Signature）：4字节，固定为“PE\0\0”（0x00004550），标识PE文件。
4. COFF文件头（IMAGE_FILE_HEADER）：20字节，记录机器类型、节区数量、时间戳、文件属性等。
5. 可选头（IMAGE_OPTIONAL_HEADER）：虽叫“可选”，对映像文件必不可少，含入口点、映像基址、对齐粒度、数据目录等。
6. 节表（Section Table）：每项40字节，记录各节名称、虚拟地址、文件偏移、大小和属性。
7. 节区（Sections）：真实数据，如`.text`（代码）、`.data`（已初始化数据）、`.rdata`（只读数据）、`.rsrc`（资源）。

### 关键字段速览

- Machine：CPU架构，0x014C是x86，0x8664是x64，0xAA64是ARM64。
- AddressOfEntryPoint：程序入口点（OEP）的RVA，加壳程序通常改到壳代码段。
- ImageBase：优先加载基址，EXE默认0x00400000，DLL默认0x10000000。
- SectionAlignment / FileAlignment：内存和文件中对齐粒度，通常0x1000和0x200，导致磁盘与内存布局不一致。
- DataDirectory：16项数组，每项含RVA和Size，指向导入表、导出表、资源、重定位表等关键数据。

### 地址换算关系

- 虚拟地址（VA） = 映像基址（ImageBase） + 相对虚拟地址（RVA）
- 文件偏移（FOA） = 目标RVA − 节区VirtualAddress + 节区PointerToRawData，先遍历节表确认所属节。

> 解析PE文件时，第一步读取DOS头的`e_lfanew`跳到PE头，再校验签名“PE\0\0”，然后依次读文件头、可选头和节表。可用`dumpbin`、CFF Explorer、PE-bear等工具查看，或自己写脚本按偏移解析。

微软官方文档《PE格式》是权威参考，覆盖所有结构体定义和字段说明：[PE 格式 - Microsoft Learn](https://docs.microsoft.com/zh-cn/windows/win32/debug/pe-format)

> 模块: 一般指任何能被装入内存中运行的可执行代码和数据的集合。
>
> - 更明确地讲，模块指的就是一个.EXE文件（又称为应用程序模块），或一个动态链接库（DLL — Dynamic Linking Library，又被称为动态链接库模块或DLL模块），或一个设备驱动程序，也可能是一个程序包含的能被另一个程序存取的数据资源

一个进程包含很多模块，意思是这个程序运行时，由多个可独立组织、职责单一的代码或功能单元共同构成，而不是一个“大而全”的单一整体。 模块是静态的代码组织单元，==进程是操作系统里正在运行的程序实例==，二者不在一个层面。

- 一个正在运行的程序实例对应的是‌**一个进程**‌，但一个程序可以同时启动多个实例，形成多个进程，如开3个浏览器窗口，对应三个独立进程，各有各的地址空间，互不干扰

简单理解：进程像一间正在开工的“工厂”，模块是工厂里的各个“车间”——有的负责界面、有的负责网络、有的负责文件读写。工厂开工时，所有车间在厂区内协同运作。

### 模块到底是什么

模块是职责单一、内部紧密相关、边界清晰的一组代码和资源的集合，强调可独立开发、测试和维护。 比如 Python 的一个 `.py` 文件、Java 的一个 `package`、Windows 里的一个 DLL 文件，都是模块的具体形式。

模块通常由两部分组成：

- 接口部分：对外暴露的访问点，定义模块提供哪些功能。
- 实现部分：内部具体代码逻辑和私有数据，外部不可见。

模块化核心价值在于：降低复杂度、提高复用性、便于团队分工，改一处不会牵动全身。

### 进程和模块的关系

==进程是操作系统进行资源分配和调度的基本单位，拥有独立地址空间==；模块是构成进程的静态或动态单元，加载到进程地址空间内运行。

==一个进程可以包含多个模块==，如一个程序加载多个 DLL；同一个模块也可能被多个进程共享使用。模块不等于进程，一个模块本身不能独立运行。

### 实际例子

- VS Code：主进程负责窗口和生命周期，渲染进程负责 UI，所有插件跑在独立的“扩展宿主进程”里；插件被打包成模块（VSIX 文件），加载后在该进程中执行。
- Windows 程序：一个 `.exe` 启动后形成进程，==运行时动态加载多个 DLL 模块，每个 DLL 提供一组相关功能==。
- 浏览器：每个标签页通常是一个独立进程，而网络、渲染、插件等模块分布在对应进程里。

所以，“一个进程有很多模块”就是在说：这个程序内部被拆成了多个边界清晰、各管一摊的组成部分，运行时统一装载到这个进程里协同工作。 这也是模块化设计在运行时的直接体现。

## 一个运行的程序实例有多少个进程

一个正在运行的程序实例对应的是一个进程，但一个程序可以同时启动多个实例，形成多个进程。

- 基本对应关系：进程就是“正在执行程序的实例”，包含程序代码、数据、寄存器等运行时资源。程序是硬盘上的静态文件，进程是它被加载到内存后的动态实体。

- 一对多的情况：同一程序可被多次运行，如开三个浏览器窗口，对应三个独立进程，各有各的地址空间，互不干扰。

- 进程与线程的区别：一个进程至少有一个线程，可包含多个线程共享进程资源，但线程不是进程，不影响进程数量。

- 特殊情况：有些程序启动后会创建子进程协助工作，如浏览器为每个标签页开新进程，但这是程序自身设计，不是“一个实例必然多个进程”的通用规则。

> 简单理解：程序是菜谱，进程是照着菜谱实际做菜的过程；同一份菜谱可同时被多个厨师使用，各做各的。

> dll注入的方式和程序正常加载dll模块的本质上是相同的，无非是通过==导入表加载==，利用==LoadLibrary加载==和一些系统机制==强制加载==
>
> - 要使程序动态加载一个dll文件 ，也就是执行程序原本没有的代码，势必要改变程序的控制流，创建一个新的线程可以做到这件事。最简单的远线程注入就是利用CreateRemoteThread和LoadLibrary两个API来完成

DLL加载到内存，本质就是让系统把DLL文件映射到进程的虚拟地址空间里，然后完成重定位、导入表绑定、TLS回调等初始化工作，之后才能正常调用里面的函数。 按加载时机分两种：程序启动时自动加载（隐式），运行中按需加载（显式）。

### 两种常规加载方式

1. 隐式加载（载入时加载）：链接时通过`.lib`文件记录DLL导出符号，程序启动时系统自动搜索并加载所需DLL，找不到直接终止进程并报错。实现简单，但启动时所有依赖DLL都要进内存，启动变慢、内存浪费。
2. 显式加载（运行时加载）：代码里调用`LoadLibrary`，拿到`HMODULE`句柄后用`GetProcAddress`获取函数地址，用完`FreeLibrary`卸载。按需加载，启动快，适合插件或可选功能。

> `LoadLibrary`返回模块句柄，`GetProcAddress`按函数名查地址。首次调用函数时才真正查找和加载DLL到内存，之后直接复用。

### 从内存直接加载（不落盘）

常规加载需要磁盘上的DLL文件。若只有内存字节流（如解密后、网络传输的），需自己实现加载器，即“内存加载DLL”或“反射式加载”。核心流程是复刻Windows加载器做的事：

1. 解析PE头：校验DOS头（MZ）、NT头（PE签名）、可选头里的`SizeOfImage`和`ImageBase`。
2. 分配内存：用`VirtualAlloc`按`SizeOfImage`分配可读写的连续内存，按节表把磁盘布局的节内容复制到对应RVA位置。
3. 修正重定位：加载地址与首选基址不一致时，遍历`.reloc`节，对每个需要修正的位置加上`实际基址 - 首选基址`。
4. 绑定导入表（IAT）：遍历导入表，用`LoadLibrary`和`GetProcAddress`解析依赖DLL及导入函数，填充IAT表项。
5. 执行TLS回调和DllMain：调用TLS回调函数，再调用入口点（通常是`DllMain`），传`DLL_PROCESS_ATTACH`通知DLL已加载。

> 注意：`LoadLibraryEx`的`LOAD_LIBRARY_AS_DATAFILE`标志只把DLL当数据读入内存，不执行重定位、不修复IAT、不调DllMain，拿到的句柄不能传给`GetProcAddress`，不算真正加载。

### ⚠️ 需要留意的坑

- 内存权限：节区需按属性设置权限，`.text`设`PAGE_EXECUTE_READ`，`.data`设`PAGE_READWRITE`，漏了会触发访问冲突。
- 静态链接CRT：内存加载的DLL最好用`/MT`静态链接，否则依赖`msvcrt.dll`等运行时库，加载后找不到CRT入口而崩溃。
- 卸载不简单：释放内存不能只`VirtualFree`，需触发`DllMain(DLL_PROCESS_DETACH)`、清理TLS槽、注销SEH处理器等，否则内存泄漏或后续加载失败。
- 标准接口可能查不到：反射式加载通常不把模块登记到PEB模块链表，`GetModuleHandle`这类标准接口未必能找到它。

常规业务优先用系统`LoadLibrary`，只有遇到“DLL不能落盘”这类硬约束时才值得自己写加载器。

## 区块表

- Size Of Raw Data
  - **单个区块（Section）在磁盘文件中所占的大小**‌。它对应的是区块数据经过 `FileAlignment` 对齐后的大小，而非整个pe文件的总大小，与内存中的 `VirtualSize` 对应
  - ==某个区块在磁盘文件中实际占用的大小==，是 ‌**FileAlignment 对齐后**‌的长度，通常为 0x200（512字节）的整数倍
- **Virtual  Size**‌：
  - 该==区块加载到内存中的实际数据大小==，即未对齐前的原始大小，通常为 `Section Alignment` 对齐后的大小

> Size Of RawData 是区块在硬盘上的“物理大小”，VirtualSize 是区块在内存里的“逻辑大小”。两者可能不同，比如 `.data` 节区可能出现 VirtualSize 大于 SizeOfRawData 的情况

整个 PE 文件的大小由 ‌**DOS 头 + NT 头 + 区块表 + 所有区块的 SizeOfRawData 之和**‌（加上文件对齐填充）决定，而非单个 `Size Of Raw Data` 字段。可选头中的 ‌`Size Of Image‌` 才是整个 PE 映像在虚拟内存中所占空间的大小

## Size Of Image‌

SizeOfImage 是 PE 文件加载到内存后整个映像的总大小，位于 `IMAGE_OPTIONAL_HEADER` 中，单位为字节，且必须是 SectionAlignment 的整数倍。

### 具体含义

- 不是文件大小：它表示 ==PE 在虚拟内存中占用空间==，而非硬盘上的文件大小。
- 覆盖范围：包含所有头、节表、节数据及对齐填充，是加载器分配内存的依据。
- 计算方式：基于所有节中 `VirtualAddress + VirtualSize` 的最大值，向上对齐到 SectionAlignment 倍数。

### 常见误区

- 修改节表 `SizeOfRawData` 或新增节后，必须重算 SizeOfImage，否则加载时映射空间不足，程序可能崩溃或报 `STATUS_ACCESS_VIOLATION`。
- 32 位和 64 位 PE 的 OptionalHeader 结构不同，解析时先通过 `Magic` 字段（0x10b 为 32 位，0x20b 为 64 位）判断，不能混用结构体。

> 简单理解：SizeOfImage 是==加载器为整个 PE 在内存中“预留的地盘大小”==，不是文件占用的磁盘空间。

### 什么是基址重定位

重定位就是把==程序的逻辑地址空间变换成内存中的实际物理地址空间==的过程，也就是说在装入时对目标程序中指令和数据的修改过程。他是实现多道程序在内存中同时运行的基础。分为==静态重定位与动态重定位==两种类型：

- 静态重定位： 在程序载入内存时一次性完成地址转换，其实现依赖连接程序的二次扫描技术；
- ==动态重定位==：在程序运行时`通过基址寄存器、页表或段表等`硬件地址变换机构`实时转换逻辑地址`，支持程序内存迁移与离散存储  
- 重定位技术应用于动态库加载、插件系统等场景

### 为什么需要基址重定位

每个`PE文件都有一个首选基地址`，它表示模块被映射到进程地址空间时最佳的装载位置。
而==代码中有许多语句都是使用直接寻址方式表示==的，这些地址是以PE文件被加载到首选基地址的条件下确定的，但如果PE文件不能被加载到首选基地址处，则代码中所有的直接寻址指令都会出现问题，这时就需要进行重定位对指令进行修正。

问题： 虚拟地址、  物理地址、 pe文件地址

虚拟地址（VA）是程序运行时看到的地址，物理地址（PA）是内存芯片上的真实地址，PE文件地址（文件偏移）则是数据在磁盘文件中的位置。三者分属不同层面，通过不同机制转换。

### 虚拟地址与物理地址

虚拟地址是操作系统给每个进程的私有地址空间，32位系统下为4GB，程序里指针的值、汇编指令中的地址都是虚拟地址。物理地址是CPU通过地址总线直接访问内存芯片的地址，唯一且固定。

转换由CPU的MMU自动完成：==虚拟地址被拆成页目录索引、页表索引和页内偏移==，通过CR3寄存器找到页目录，再查页表得到物理页框号，最后加上偏移得到物理地址。整个过程对程序透明，程序只操作虚拟地址。

> 关键区别：虚拟地址是逻辑概念，每个进程独立；物理地址是硬件真实位置，由操作系统和MMU管理，用户程序不直接操作。

### PE文件地址

==PE文件涉及三种地址==，容易混淆：

1. 文件偏移地址（File Offset）：数据在磁盘上相对于文件头的偏移，用十六进制编辑器打开看到的地址就是它。
2. 相对虚拟地址（RVA）：数据在内存中相对于映像基址（Image Base）的偏移，是PE头里主要使用的形式。
3. 虚拟地址（VA）：程序运行时数据在内存中的实际虚拟地址，`VA = ImageBase + RVA`。

### 地址转换公式

==RVA与VA转换==：

```
VA = ImageBase + RVA
RVA = VA - ImageBase
```

EXE默认ImageBase为0x400000，DLL为0x10000000。

==文件偏移与RVA转换==：

```
File Offset = PointerToRawData + (RVA - VirtualAddress)
```

其中VirtualAddress是区段在内存中的起始RVA，PointerToRawData是区段在文件中的起始偏移。需先遍历区段表，确认RVA落在哪个区段的`VirtualAddress`到`VirtualAddress + VirtualSize`范围内，再用该区段参数计算。

> 注意：PE头（DOS头、NT头、区段表）在内存和磁盘中的偏移一致，不需要转换；只有区段内的数据才需要按上述公式换算。

### 实际应用场景

做逆向或分析PE文件时，常见操作是：用十六进制工具打开文件，看到某处文件偏移为0x400，想找它加载到内存后的虚拟地址。先定位该偏移属于哪个区段，假设属`.text`节（VirtualAddress=0x1000，PointerToRawData=0x400），则`RVA = 0x400 - 0x400 + 0x1000 = 0x1000`，`VA = 0x400000 + 0x1000 = 0x401000`。

反过来，调试器里看到某指令在0x401325，想修改磁盘文件，则先转RVA=0x1325，再算`File Offset = 0x400 + (0x1325 - 0x1000) = 0x725`，直接定位到文件偏移0x725处修改字节。

文件对齐和内存对齐不同（通常文件对齐0x200，内存对齐0x1000），导致加载后区段间出现“空洞”，所以文件偏移和RVA不能简单等同。另外，有些区段（如`.bss`）在内存中占空间但磁盘上不占数据，这类区段没有对应的文件偏移。

## 求文件中的地址

**相对虚拟地址(RVA) 与 文件偏移地址转换(FOA)** 

==**目标地址在文件中的地址 = 该区块的 PointerToRawData + (目标RVA − 该区块的 VirtualAddress)**==

> 关键在于：RVA是相对于内存映像基址的偏移，而`区块在文件中的起始位置`（PointerToRawData）和它`在内存中的起始位置`（VirtualAddress）通常不相等，因为文件对齐（通常0x200）和内存对齐（通常0x1000）粒度不同。

### 正确转换步骤

1. ==确定目标RVA落在哪个区块==：遍历节表，找到满足 `VirtualAddress ≤ RVA < VirtualAddress + VirtualSize` 的区块。
2. 计算区块内偏移：`偏移量 = RVA − 该区块的 VirtualAddress`。
3. 加上区块在文件中的起始位置：`文件偏移 = 该区块的 PointerToRawData + 偏移量`。

> 公式可以写成：`File Offset = PointerToRawData + (RVA − VirtualAddress)`

### 举个例子

假设某PE文件的节表信息如下：

| 区块名 | VirtualAddress | PointerToRawData | SizeOfRawData |
| ------ | -------------- | ---------------- | ------------- |
| .text  | 0x1000         | 0x400            | 0x800         |
| .data  | 0x2000         | 0xC00            | 0x200         |

如果目标 RVA 是 0x1050：

1. 0x1050 落在.text 区块（0x1000 ≤ 0x1050 < 0x1000 + 0x850）
2. 区块内偏移 = 0x1050 − 0x1000 = 0x50
3. 文件偏移 = 0x400 + 0x50 = 0x450 

### ⚠️ 两个需要注意的地方

- PE头区域是特例：如果目标RVA落在PE头（小于第一个区块的VirtualAddress），文件偏移和RVA相等，不需要转换。
- VirtualSize和SizeOfRawData可能不一致：判断RVA属于哪个区块时以VirtualSize为准，但文件偏移计算出来后，要确认偏移量小于SizeOfRawData，否则该数据只在内存中存在，文件中没有对应内容。

你之前问过PE结构和内存管理相关的内容，这个转换是逆向分析和二进制修改的基础，理解对齐差异是掌握它的关键。

## VA/RVA 到 FOA 的转换

==PE文件求目标地址在文件中的位置，核心就是做 VA/RVA 到 FOA 的转换==。关键在于不能直接用目标地址减文件头，必须通过节表（Section Table）来映射，因为文件对齐（通常0x200）和内存对齐（通常0x1000）不一致，导致同一数据在磁盘和内存中的偏移不同。

### 转换步骤

1. 判断输入地址类型：先确认目标地址是 VA（虚拟地址） 还是 RVA（相对虚拟地址）。如果是 VA，先算出 RVA：`RVA = VA - ImageBase`（ImageBase 通常为 0x400000）。
2. ==定位所属节==：遍历节表，找到 RVA 落在哪个节的 `[VirtualAddress, VirtualAddress + VirtualSize)` 区间内。
3. 套用公式：`FOA = PointerToRawData + (RVA - VirtualAddress)`，其中 `PointerToRawData` 是节在文件中的起始偏移，`VirtualAddress` 是节在内存中的起始 RVA。
4. 特殊处理：如果 RVA 小于第一个节的 VirtualAddress，说明落在 PE 头部区域，此时 FOA = RVA（头部在文件和内存中偏移一致）。

> 举例：某程序 ImageBase=0x400000，目标 VA=0x40150D，.text 节 VirtualAddress=0x1000，PointerToRawData=0x600。RVA=0x150D，属于.text 节，FOA = 0x600 + (0x150D - 0x1000) = 0xB0D。用十六进制编辑器跳到 0xB0D 就能看到对应指令。

⚠️ 注意事项

- 判断区间用 VirtualSize：判断 RVA 属于哪个节时，优先用 `VirtualSize`（内存实际大小）而不是 `SizeOfRawData`（文件对齐后大小），否则可能误判节归属。
- 警惕无文件数据的节：有些节（如.bss 或未初始化数据节）在内存中有空间但磁盘上不占数据，RVA 落在这类节内时没有对应的 FOA，转换无意义。
- 验证结果：转换后可用 LordPE{id="entity_1"} 的“位置计算器”或 010 Editor{id="entity_2"} 的 PE 模板交叉验证，避免手算出错。

## 虚拟地址和物理地址

[虚拟地址是不是和物理地址一样_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=%E8%99%9A%E6%8B%9F%E5%9C%B0%E5%9D%80%E6%98%AF%E4%B8%8D%E6%98%AF%E5%92%8C%E7%89%A9%E7%90%86%E5%9C%B0%E5%9D%80%E4%B8%80%E6%A0%B7)  

虚拟地址和物理地址不是一回事。==虚拟地址是程序看到的逻辑地址==，物理地址是硬件实际访问内存的真实地址，两者通过MMU（内存管理单元）和页表建立映射关系。

### 核心区别

1. 本质不同：虚拟地址是操作系统给每个进程分配的独立地址空间编号，只是抽象概念；物理地址是放在地址总线上的真实地址，直接对应内存芯片的存储单元。

2. 空间大小不同：虚拟地址空间通常远大于物理内存。32位系统每个进程有4GB虚拟空间，实际物理内存可能只有1GB甚至更少。

3. 可见性不同：程序中的指针（如C语言`&`取地址）拿到的是虚拟地址，用户和进程可见；物理地址对进程透明，用户无法直接获取或操作。

4. 连续性不同：虚拟地址是连续的，程序员无需关心物理内存碎片；物理地址可能离散分布，由操作系统把分散的物理页拼接成连续的虚拟空间。

### 转换过程

==CPU执行指令访问内存时，MMU根据页表自动把虚拟地址转换成物理地址==：

- 虚拟地址拆分为页目录索引、页表索引和页内偏移
- 通过CR3寄存器找到页目录，再逐级查页表找到物理页框号
- 物理页框号加上页内偏移，得到最终物理地址

### ⚠️ 一个容易混淆的点

CPU启动早期（实模式）和Bootloader阶段，没有虚拟地址概念，直接使用物理地址。==只有进入保护模式并开启分页后，程序才运行在虚拟地址空间中==。

### 为什么这样设计

- 进程隔离：每个进程有独立虚拟空间，无法直接访问其他进程内存，安全。
- 内存保护：页表记录权限属性，越权访问在地址转换阶段就被拦截。
- 效率提升：物理内存不够时可将部分数据换出到磁盘，程序无感知。
- 解耦管理：进程管理和内存管理互不干扰，程序可加载到物理内存任意位置。

## ==如何通过RVA得到物理地址==

[如何通过RVA得到物理地址_百度搜索](https://www.baidu.com/s?ie=UTF-8&wd=%E5%A6%82%E4%BD%95%E9%80%9A%E8%BF%87RVA%E5%BE%97%E5%88%B0%E7%89%A9%E7%90%86%E5%9C%B0%E5%9D%80)  

RVA（相对虚拟地址）本身是内存中的偏移量，要得到真正的“物理地址”需要分两步：==先转成VA（虚拟地址），再通过分页机制转成物理地址==。 但如果你说的“物理地址”是指==PE文件在磁盘上的文件偏移（FOA）==，那直接用节表公式换算即可。下面把两种场景都讲清楚。

### 场景一：RVA → 文件偏移（FOA）

这是逆向分析中最常见的需求，比如在反汇编器里看到某个RVA，想用十六进制编辑器定位到磁盘上对应的字节。

核心公式：
```
FOA = 得到的目标RVA - 节.VirtualAddress + 节.PointerToRawData
```

具体步骤：
1. 遍历节表，找到目标RVA落在哪个节内。判断条件是：
   ```
   节.VirtualAddress <= RVA < 节.VirtualAddress + 节.VirtualSize
   ```
2. 套用公式：用RVA减去该节的起始RVA，得到节内偏移；再加上该节在文件中的起始偏移（PointerToRawData），就是FOA。

举个实例：假设`.text`节的VirtualAddress是`0x1000`，PointerToRawData是`0x400`。若RVA为`0x1234`，则：
```
FOA = 0x1234 - 0x1000 + 0x400 = 0x634
```
跳到文件偏移`0x634`处，就能找到对应的数据。

> 注意：如果RVA落在PE头部区域（小于第一个节的VirtualAddress），通常RVA和FOA相等，不需要走节表公式。

### 场景二：RVA → 运行时物理地址

如果你问的是程序运行时的真实物理内存地址，那要经过两级转换：

1. RVA → VA：先加上模块基址（ImageBase）。
   ```
   VA = ImageBase + RVA
   ```
   比如ImageBase为`0x00400000`，RVA为`0x1000`，则VA为`0x00401000`。

2. VA → 物理地址：由CPU的MMU通过页表自动完成。对于32位系统，虚拟地址被拆成三部分：
   - 高10位：页目录索引（PDE）
   - 中10位：页表索引（PTE）
   - 低12位：页内偏移

   CPU从CR3寄存器找到页目录，逐级查表得到物理页基址，最后加上页内偏移，就是物理地址。

> 这个转换过程由==硬件自动完成==，程序里一般拿不到直接结果。如果在内核态或驱动开发中需要手动查页表，才需要关注CR3和页表结构。

### ⚠️ 容易混淆的地方

- RVA和VA都是内存地址概念，不是磁盘文件偏移。只有加上ImageBase才是真正的VA，只有经过节表换算才是FOA。
- 不要把RVA直接当FOA用，这是新手最常见的错误，会导致读出来的数据全是乱的。
- VirtualSize和SizeOfRawData可能不一致：判断RVA是否落在节内时，严格用VirtualSize；但加载器实际分配空间按对齐后大小，边界情况要留意。

## pe文件找出FOA有什么用

[PE知识复习之PE的RVA与FOA的转换](https://cloud.tencent.com/developer/article/1432559)  [文件偏移地址_百度百科](https://baike.baidu.com/item/%E6%96%87%E4%BB%B6%E5%81%8F%E7%A7%BB%E5%9C%B0%E5%9D%80/9071104)  [PE文件：VA、RVA和FOA](https://blog.csdn.net/weixin_43742894/article/details/105235629)  [ PE系列之导入表解析与IAT Hook技术](https://bbs.kanxue.com/thread-269726-1.htm)  

在PE（Portable Executable）文件分析、逆向工程及软件开发中，找出FOA（File Offset Address，文件偏移地址）的核心作用在于建立“磁盘文件”与“内存映像”之间的映射关系。

由于PE文件在磁盘存储和加载到内存运行时，其数据布局存在显著差异（主要是对齐方式不同），直接通过内存地址无法在十六进制编辑器中定位数据，反之亦然。FOA是解决这一问题的关键桥梁。

> 为什么需要RVA转FOA？  [文件偏移地址_百度百科](https://baike.baidu.com/item/%E6%96%87%E4%BB%B6%E5%81%8F%E7%A7%BB%E5%9C%B0%E5%9D%80/9071104)  
>
> - 因为PE文件在磁盘上以文件偏移的形式存储，而在内存中以虚拟地址的形式加载，RVA转FOA用于在文件中定位数据

### 以下是找出FOA的主要用途：

1. 静态分析与数据定位

  这是FOA最基础且最常用的场景。逆向分析师或安全研究人员通常在静态环境（如使用 WinHex、010 Editor、IDA Pro 的视图模式）下工作。
- 定位关键数据：当通过动态调试（如 x64dbg、OllyDbg）获取到某个字符串、全局变量或硬编码密钥的虚拟地址（VA）或相对虚拟地址（RVA）时，必须将其转换为FOA，才能在磁盘上的二进制文件中找到该数据的原始字节，从而进行修改或提取。
- 解析数据结构：PE文件中的许多重要结构（如导入表、导出表、重定位表、资源表）在数据目录中仅给出RVA。要手动解析这些表的内容，必须先将RVA转换为FOA，才能从文件中读取具体的结构体数据。

2. 文件修改与补丁制作（Patching）

  在对可执行文件进行汉化、去广告、破解或修复Bug时，操作对象是磁盘上的文件。
- 精准修改：如果你知道需要修改的代码或数据在内存中的位置（RVA/VA），必须计算出对应的FOA，才能在文件中准确跳转并修改字节。如果直接按RVA去文件中找，由于内存对齐（通常为4KB）和文件对齐（通常为512B）的差异，会导致定位错误。
- 添加新节或数据：在向PE文件中注入代码或数据时，需要计算新数据在文件中的写入位置（FOA），并相应更新节表头中的`PointerToRawData`等字段。

3. 恶意代码分析与免杀研究

  在安全领域，分析恶意样本或开发检测工具时，FOA至关重要。
- 壳与加密分析：许多加壳程序会混淆内存布局。通过分析FOA与RVA的转换关系，可以识别出哪些节区是被压缩或加密的，以及它们在解压后的内存对应关系。
- 傀儡进程与注入：在实现进程注入技术（如傀儡进程）时，需要将恶意PE文件的内容写入目标进程的内存空间。此时需要频繁进行FOA到VA的转换，以确保写入的数据在目标进程内存中能正确执行，同时可能需要修复重定位表，这依赖于准确的地址映射。

4. 理解PE加载机制

  对于系统程序员或驱动开发者，理解FOA有助于深入掌握Windows加载器（Loader）的工作原理。
- 对齐差异处理：FOA的存在揭示了磁盘存储效率（小对齐）与内存执行效率（大页对齐）之间的权衡。理解这一转换有助于优化大型程序的加载性能或处理特殊的PE畸形结构。

---

### 核心原理简述

PE文件在磁盘和内存中的布局差异主要体现在节区（Section）的对齐上：

- 磁盘上：节区按`FileAlignment`（通常512字节）对齐，紧凑存储。
- 内存中：节区按`SectionAlignment`（通常4096字节）对齐，稀疏分布。

因此，RVA ≠ FOA（除非在PE头部区域或对齐值相同）。转换公式依赖于节表（Section Table）中的两个关键字段：
- `VirtualAddress` (RVA起始)
- `PointerToRawData` (FOA起始)

转换逻辑：

1. 确定目标地址属于哪个节区。
2. 计算该地址相对于节区起始位置的偏移量（这个偏移量在磁盘和内存中是相同的）。
3. 将该偏移量加上节区在磁盘上的起始FOA，即得到最终的FOA。

总结：找出FOA是为了在磁盘文件层面精确定位和操作那些在内存中以虚拟地址形式存在的数据，它是连接静态文件分析与动态内存行为的必要纽带。

## 从汇编角度理解未初始化的数据

[C语言全局未初始化数据段分析](https://www.cnblogs.com/james1207/p/3362277.html)  

[未初始化变量](https://blog.csdn.net/hjrcrj/article/details/51612273)  

从汇编角度看，==未初始化的数据就是只分配空间、不写初值==，最终落在 `.bss` 段里。它和已初始化数据最大的区别在于：不占用可执行文件空间，程序加载时由系统自动清零。下面拆开讲。

### 汇编层面怎么定义

用 `?` 表示不初始化，`DUP` 配合 `?` 可批量申请空间：

```assembly
buffer  DB 64 DUP(?)    ; 64个未初始化字节
count   DW ?            ; 1个未初始化字
matrix  DD 10 DUP(?)    ; 10个未初始化双字
```

`?` 只告诉汇编器“留空间”，不往里面写值。对应的段是 `.bss`（MASM 里也可写成 `.data?`），而 `DB 0` 这类带初值的则放进 `.data` 段。

### 关键：为什么单独分出.bss

从汇编和链接角度，核心原因就一个字：省空间。

- `.data` 段的内容直接写进可执行文件，程序加载时从文件拷贝到内存。若有个 100KB 的数组全初始化为 0，文件里就得实实在在存 100KB 的 0。
- `.bss` 段只记录变量名和大小，不存实际值。可执行文件里只有“这里需要 100KB”这么一条记录，加载时系统直接分配内存并清零。

> 可以这样理解：`.data` 像搬家时把东西全打包带走，`.bss` 像只告诉搬家公司“这里要放一个柜子”，柜子到了新家才现组装。

### 加载时发生了什么

程序启动后，进入 `main()` 之前，C 运行时启动代码（crt0 之类）会主动把 `.bss` 段对应的内存区域清零。“未初始化变量默认是 0”不是硬件天然保证的，而是启动代码做出来的。

汇编里对应操作通常就是一段循环或 `rep stosd` 指令，把 `.bss` 起始地址到结束地址的区域全部写 0。

### 未初始化数据的真实风险

这里有个容易混淆的地方：汇编里的 `?` 和高级语言里的“未初始化”不完全是一回事。

- 汇编里用 `?` 定义的全局/静态变量，最终进 `.bss`，运行时会被清零，读出来是 0。
- 但局部变量（栈上分配）不经过 `.bss`，若没赋初值就直接读，拿到的是栈上残留的随机值。从汇编看，编译器在 Debug 模式下会插入 `__RTC_UninitUse` 之类的检查，运行时发现读未初始化变量就报错；Release 模式下则直接读，结果不可预测。

所以从汇编角度可以总结成一句话：未初始化数据 = 只占空间、不占文件、加载时清零，但这条只对全局/静态变量成立，局部变量得自己小心。

> 问题： 未初始化数据既然只分配空间,为什么又说它不占用可执行文件空间？

未初始化数据不占用可执行文件空间，指的是不存储实际数据内容，但文件里会保留一段描述信息（大小、位置等元数据）。所以“只分配空间”和“不占用文件空间”是从不同层面说的：==分配的是运行时的内存空间，不占的是磁盘上的文件存储空间==。

### 两个“空间”的区别

1. 磁盘上的可执行文件空间：未初始化变量（如 `int global_var;`）的值全是0，没必要在文件里逐个字节存0。链接器只在文件头记录“这块区域有多大”，实际数据内容不写入文件，所以文件体积几乎不变。
2. 运行时的内存空间：程序加载时，操作系统根据记录的大小，在进程地址空间里分配对应内存并清零。这块内存是真实存在的，程序运行中确实占着虚拟地址空间。

### 文件里的“占位”是怎么回事

可执行文件（如ELF）中，BSS段以`NOBITS`类型存在，意思是“不占文件内容空间”，但段表里有条目记录其起始地址和大小。

> 可以这样理解：就像一张桌子（可执行文件）上放了一张纸条，写着“这里将来要放1MB东西”，但纸条本身不占1MB空间。等真正要用桌子（程序运行时），才按纸条上的说明把1MB东西摆出来。

### 一个容易混淆的点

- 不占文件空间 $≠$ 不占内存空间。程序未运行时，BSS变量不占磁盘；程序运行时，操作系统会分配对应内存并清零。
- 初始化为0的变量同样放在BSS段，也不占文件空间，因为0不需要存储。
- 非零初始化的变量（如 `int c = 42;`）则放在`.data`段，初始值必须写入文件，会直接增大文件体积。

验证方法：用`size`命令查看各段大小，或声明一个大数组（如`char buf[1MB];`）后对比编译前后文件体积，几乎不变。

## 从汇编角度理解局部和全局变量

[用汇编语言研究C语言的全局变量、局部变量、参数、返回值放在哪里](https://www.cnblogs.com/amanlikethis/p/3570832.html)  [汇编语言](https://cloud.tencent.com/developer/article/1549091)  [全局和局部变量](https://zhuanlan.zhihu.com/p/406610204)  [汇编语言](https://developer.aliyun.com/article/876941)  [从汇编语言角度探讨全局变量和局部变量](https://blog.csdn.net/James201904/article/details/102646574)  [汇编视角下的变量内存布局：全局与局部变量的本质区别](https://blog.csdn.net/weixin_31102231/article/details/168351823)   [全局变量和局部变量的区别](https://wenku.baidu.com/view/78e3f80f83c24028915f804d2b160b4e767f81ca.html?_wkts_=1792816573966)  

全局变量在汇编里是数据段中固定地址的内存，局部变量则是栈帧里相对于 rbp/rsp 的偏移量。编译器在编译期就为全局变量分配好固定地址，整个程序运行期间不变；局部变量只在函数调用时于栈上临时开辟，函数返回即失效。

> 我的理解： 全局变量是数据段固定地址； 局部变量使用栈空间

### 全局变量：数据段里的“常驻居民”

全局变量存放在 `.data`（已初始化）或 `.bss`（未初始化）段，汇编里通过直接地址或 RIP 相对寻址访问。

```c
int g_init = 100;   // →.data 段
int g_uninit;       // →.bss 段
```

对应的汇编可能是：

```asm
mov eax, [rip + 0x2ee0]   ; 读取 g_init，地址固定
mov [rip + 0x2ed7], eax   ; 写回 g_init
```

关键特征：

1. 地址固定：链接时确定，程序运行期间不变，整个进程生命周期都有效。
2. 未初始化变量自动清零：`.bss` 段不占磁盘空间，加载时由操作系统清零。
3. 任何函数都能访问：通过符号名直接引用，无栈帧依赖。

### 局部变量：栈帧里的“临时工”

局部变量在汇编里没有名字，只有 `[rbp-4]`、`[rbp-8]` 这类偏移量。函数调用时，通过调整 `rsp` 在栈上开辟空间，用 `rbp` 作锚点访问。

```c
void func() {
    int x = 10;   // → [rbp-4]
    int y = 20;   // → [rbp-8]
}
```

对应的汇编是：

```asm
push rbp
mov rbp, rsp
sub rsp, 16        ; 开辟局部变量空间
mov [rbp-4], 10    ; x
mov [rbp-8], 20    ; y
...
mov rsp, rbp
pop rbp
ret
```

关键特征：

1. 生命周期绑定函数调用：进入函数时开辟，返回时释放，地址可能被后续调用覆盖。
2. 访问靠偏移量：`rbp-4`、`rbp-8` 这些偏移是编译期确定的常量，汇编里看不到变量名。
3. 可能被优化到寄存器：开启优化后，频繁使用的局部变量直接放进 `eax`、`edx` 等寄存器，根本不落地栈。

### 两者对比

| 维度             | 全局变量                | 局部变量           |
| ---------------- | ----------------------- | ------------------ |
| 存储位置         | `.data` / `.bss` 段     | 栈帧内             |
| 地址方式         | 固定地址或 RIP 相对寻址 | `[rbp-偏移]`       |
| 生命周期         | 整个程序运行期          | 函数调用期间       |
| 汇编里是否有名字 | 有符号名                | 无名字，只有偏移量 |
| 访问速度         | 稍慢（内存访问）        | 快（寄存器或栈）   |

> ⚠️ 一个容易混淆的点：`static` 局部变量是个特例——它在汇编里被当作全局变量处理，放在 `.data` 或 `.bss` 段，但符号名做了内部化处理，其他函数无法引用。所以它“作用域是局部的，生命周期是全局的”。

### 为什么这样设计

1. 效率：全局变量地址固定，无需每次计算；局部变量用 `rbp` 加偏移，一条指令就能得到地址，且栈空间自动复用，管理开销极低。
2. 并发安全：局部变量天然线程安全（每线程有自己的栈）；全局变量则需锁保护，否则多线程读写会出竞态条件。
3. 调试启示：逆向分析时，看到固定地址访问大概率是全局变量，看到 `[rbp-偏移]` 则是局部变量。但优化后的代码可能把局部变量提升到寄存器，需结合上下文判断。

# 重定位表

## 基址重定位

**基址重定位（base relocation）**，简单说就是：程序在内存里被放到哪个物理位置，就用一个“基址寄存器”记住这个起始地址，CPU 每次访存时自动把程序里的相对地址加上基址，得到真正的物理地址。这样程序不必在装载时修改自己的指令，就能被放到内存任意位置运行。

### 为什么需要它

程序编译链接后，里面的地址通常是“从 0 开始”的逻辑地址（比如指令 `JMP 0x1000`）。但操作系统把程序装入内存时，可能放在 0x0040_0000，也可能放在 0x0080_0000。如果地址不改，程序就会跑飞。重定位解决的就是“逻辑地址 → 物理地址”的映射问题，它让多道程序可以各自拥有独立的地址空间，也支持内存紧凑（compaction）后程序继续运行。

### 静态重定位 vs 动态重定位

- **静态重定位**：在程序**装入内存时**（加载期或链接期）一次性把所有地址改写成绝对地址。优点是不需要额外硬件；缺点是程序一旦装入就不能移动，且必须连续分配空间。
- **动态重定位**：装入时不改程序，**每次访存时由硬件实时换算**。优点是程序可在内存中移动、支持虚拟内存和共享，代价是需要专门的地址转换硬件。基址重定位通常指的就是这种。

### 硬件机制

核心是两个寄存器（由操作系统在内核态设置，用户程序无法篡改）：

- **基址寄存器（base register / 重定位寄存器）**：存放该进程在物理内存中的起始地址。
- **界限寄存器（limit register）**：存放程序长度，用于越界保护。

地址转换过程：

```
若 逻辑地址 < 界限寄存器：
    物理地址 = 基址寄存器 + 逻辑地址
否则：
    触发越界异常（Segmentation Fault / 地址越界中断）
```

这个加法由 CPU 内部的地址转换电路（MMU 的一部分）完成，对程序完全透明。

**举个例子**：基址寄存器 = 0x0040_0000，界限寄存器 = 0x0000_8000（32 KB）。

- 指令访问逻辑地址 0x0000_1234 → 物理地址 0x0040_1234，合法。
- 访问逻辑地址 0x0000_9000 → 超过界限 0x8000，产生越界异常，不会写到别的进程空间里。

### 和分段、分页的关系

- 基址重定位本质就是**最简化的分段**：整个程序作为一个段，一个基址加一个限长。x86 的段寄存器（CS/DS/SS 等）配合段基址，就是这套机制的工程化版本。
- 进一步把段切成固定大小的页，用**页表**做映射，就从“一个基址”扩展成“每页一个基址”，能解决外部碎片、支持按需调页和写时复制。可以说基址重定位是分段/分页地址转换的雏形。
- 在支持位置无关代码（PIC）和共享库的系统里，重定位还会在链接期/加载期通过 GOT、重定位表（`.rela` 段）完成，动态链接器 `ld.so` 会按实际加载地址修正符号地址；配合 ASLR，每次启动基址都随机化，提升安全性。

### 优缺点小结

优点：程序可浮动装载、支持内存紧凑与多道并发、提供基本的地址空间隔离与越界保护、无需修改程序本身。 缺点：仍需要连续的空闲分区（会产生外部碎片）、每次访存多一次加法与比较（现代 CPU 由硬件流水线掩盖，开销很小）、单基址粒度太粗，无法实现细粒度共享与虚拟内存。

### 常见易混点

1. 基址重定位换算的是**物理地址**；而“基址 + 偏移”在分页体系里换算的可能是下一级页表地址，别把两级概念混在一起。
2. 静态重定位改的是**程序里的地址值**，动态重定位改的是**硬件换算行为**，程序镜像始终不变。
3. 界限检查必须在加法之前或与之并行完成，否则越界访问可能已经发生。
4. 基址寄存器属于**特权资源**，只能在内核态通过加载指令设置，进程切换时由操作系统保存/恢复。

## PE文件的重定位表

PE 的重定位表（Base Relocation Table，`.reloc`）就是上一轮说的“基址重定位”在 Windows 可执行文件里的**具体数据载体**：它不存储新地址，只存储“哪些位置写死了绝对地址、该按什么宽度修正”，真正的修正值由加载器在运行时用 `实际基址 - 首选基址` 算出来。

### 一、什么时候才会用到

链接器给每个 PE 一个首选基址（`OptionalHeader.ImageBase`，如 0x400000）。加载时如果这块地址空闲，直接映射，重定位表形同虚设；一旦被占用（典型场景：DLL 依赖冲突、ASLR 随机化、手动映射到任意内存），加载器就必须按重定位表逐个打补丁 。

- DLL 几乎必然带 `.reloc`，因为它无法保证加载到首选基址 。
- 老资料说“EXE 不需要重定位表”已过时：ASLR 默认开启后，现代 EXE 通常也带 `.reloc`；若特征位 `IMAGE_FILE_RELOCS_STRIPPED`（0x0001）被置位，说明重定位信息被剥离，此时基址一变就无法正常运行 。

### 二、在文件中的位置

- 目录项：`OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_BASERELOC]`，即第 6 项（索引 5），给出重定位表的 **RVA 和大小** 。
- 物理位置：通常单独放在名为 `.reloc` 的节中 。
- 从文件里读时要先做 RVA→FOA 转换：`FOA = RVA - 节.VirtualAddress + 节.PointerToRawData` ；在内存中（手动映射场景）则直接 `镜像基址 + RVA` 即可 。

### 三、结构：块头 + 紧凑的 16 位项

重定位表不是一个定长数组，而是**一串紧密排列的“重定位块”**，每个块对应一个 4KB 页面 ：

```
typedef struct _IMAGE_BASE_RELOCATION {
    DWORD VirtualAddress;   // 本页起始 RVA（4KB 对齐）
    DWORD SizeOfBlock;      // 本块总字节数，含这 8 字节头
    // WORD TypeOffset[1];  // 紧随其后的重定位项数组（变长）
} IMAGE_BASE_RELOCATION;
```

每个重定位项只有 **2 字节（WORD）**：高 4 位是类型，低 12 位是页内偏移 。

```
| 15..12 类型(4bit) | 11..0 页内偏移(12bit) |
```

几个关键约定：

- **项数 = (SizeOfBlock - 8) / 2** 。
- **被修正位置的 RVA = VirtualAddress + 低 12 位偏移**，再叠加镜像基址得到 VA 。
- 用 12 位是因为页大小 4KB = 2¹²，偏移刚好够用，多出的 4 位拿来存类型，这是为省空间的设计 。
- 块必须 4 字节（DWORD）对齐，块尾常用类型 0 的项做填充 。
- 表以一个 `VirtualAddress` 与 `SizeOfBlock` 全为 0 的块作为结束标记 。

### 四、重定位类型

| 常量                     | 值       | 含义                                       |
| ------------------------ | -------- | ------------------------------------------ |
| IMAGE_REL_BASED_ABSOLUTE | 0        | 不修正，仅作对齐填充                       |
| IMAGE_REL_BASED_HIGH     | 1        | 只修正 32 位地址的高 16 位                 |
| IMAGE_REL_BASED_LOW      | 2        | 只修正低 16 位                             |
| IMAGE_REL_BASED_HIGHLOW  | 3        | 修正整个 32 位字段，x86 最常见             |
| IMAGE_REL_BASED_HIGHADJ  | 4        | 占两个项，本项为高 16 位、下一项为低 16 位 |
| IMAGE_REL_BASED_DIR64    | 10 (0xA) | 修正 64 位地址，x64 最常见                 |

（0x5~0x9 多为 MIPS 等平台专用或保留值 。）

### 五、修正算法

核心就是 delta 加法：

```
delta = 实际加载基址 - OptionalHeader.ImageBase
若 delta == 0，无需处理
遍历每个块（VirtualAddress != 0）：
    dest = 镜像基址 + block->VirtualAddress
    对每项：
        type   = entry >> 12
        offset = entry & 0xFFF
        switch (type):
            HIGHLOW: *(DWORD*)(dest + offset) += (DWORD)delta
            DIR64:   *(ULONGLONG*)(dest + offset) += delta
            HIGH:    *(WORD*)(dest + offset) += HIWORD(delta)
            LOW:     *(WORD*)(dest + offset) += LOWORD(delta)
            ABSOLUTE: 跳过
    块指针 += block->SizeOfBlock
```

这与内存加载器（如 MemoryModule 类实现）里的 `PerformBaseRelocation` 逻辑一致：x86 走 HIGHLOW、x64 走 DIR64，若 delta 非 0 却没有重定位信息，加载通常直接失败 。

**手算例子**：某块 `VirtualAddress = 0x11000`，`SizeOfBlock = 0x68`，则项数为 (0x68-8)/2 = 0x30 个；若某项为 0x3698，高 4 位为 3（HIGHLOW），低 12 位为 0x698，需修正的 RVA = 0x11000 + 0x698 = 0x11698 。假设镜像首选基址 0x400000、实际加载到 0x500000，则 delta = 0x100000，把 VA 0x511698 处的 32 位值加上 0x100000 即可。

### 六、实践中的坑

1. **只修正绝对地址**。指令里用相对寻址（x86 的 `EIP+disp`、x64 的 RIP-relative）不需要重定位，这也是 x64 代码重定位项明显变少的原因之一；反之，大量全局变量/常量的绝对引用会让 `.reloc` 膨胀 。
2. **别把偏移当完整地址**。低 12 位必须加回 `VirtualAddress` 才是 RVA，直接当地址用是新手最常见的错误 。
3. **结束判断用 SizeOfBlock 或全 0 块**，不能用“数组长度”，因为目录项给的 Size 有时不可靠，实践中以 `VirtualAddress == 0` 收尾更稳 。
4. **HIGHADJ 会消耗两个项**，遍历时若不做特殊处理会错位 。
5. **磁盘格式与内存格式可能不同**：较新链接器会生成压缩/紧凑形式的重定位数据，加载器在内存中展开后再处理；自己写解析器时若发现块结构对不上，先确认是不是这种形式（具体布局建议以实测和官方头文件为准）。
6. **`.reloc` 常被视为可丢弃数据**：加载器应用完重定位后，这部分内存通常不再需要，因此运行时 dump 里可能看不到完整的 `.reloc` 内容。
7. **手动映射 / 进程镂空 / 内核映射**必须自己完成这一步，否则任何硬编码指针都会指向旧基址而崩溃 。

### 七、怎么快速查看

- `dumpbin /relocations your.dll`（或 `/headers` 看目录项 5），能直接列出页 RVA、类型和偏移。
- CFF Explorer、PE-bear、010 Editor 的 PE 模板可可视化浏览 `.reloc` 块 。
- 脚本化用 Python 的 `pefile`，遍历 `DIRECTORY_ENTRY_BASERELOC` 即可统计各类型数量。
