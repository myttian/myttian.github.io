# 调试工具

最主流的选择是 x64dbg，它被普遍认为是 OllyDbg 的现代继任者，支持 32 位和 64 位程序，更新活跃。

### 主要替代方案

1. x64dbg（首选）：开源、免费，界面和操作逻辑继承自 OllyDbg，F2/F7/F8/F9 等快捷键基本一致，迁移成本低。原生支持 64 位调试，内置脚本引擎、PDB 符号加载，插件生态活跃（如 Scylla 脱壳、TitanHide 反反调试）。
2. WinDbg：微软官方调试器，适合内核态调试、崩溃转储分析。用户态逆向不如 x64dbg 直观，但系统级问题必须用它。
3. IDA Pro：静态分析行业标准，配合 x64dbg 使用效果最好——先用 IDA 静态理解全局，再用 x64dbg 动态验证细节。
4. edb-debugger：跨平台调试器，支持 Linux/macOS/Windows，可调 ARM 架构，适合非 Windows 平台的逆向工作。
5. Visual Studio：如果只是做汇编语言实验、有源码的情况下，VS2022 的反汇编窗口也能替代 OllyDbg，且更高效直观。

### 关键对比

| 维度       | OllyDbg    | x64dbg              |
| ---------- | ---------- | ------------------- |
| 支持 64 位 | ❌ 不支持   | ✅ 原生支持          |
| 维护状态   | 已停更     | 持续活跃开源        |
| 界面       | 老旧       | Qt 框架，可定制主题 |
| 插件生态   | 丰富但老化 | 活跃，兼容性强      |
| PDB 符号   | ❌          | ✅ 支持              |

> ⚠️ 如果只调 32 位老程序，OllyDbg 依然能用，但遇到反调试、加壳或 64 位目标时，建议直接换 x64dbg。

### 迁移建议

从 OllyDbg 换到 x64dbg 基本无痛：快捷键一样，界面布局相似。建议先装 ScyllaHide（反反调试）和 xAnalyzer（自动注释）这两个插件，配合你正在研究的 PE 结构和内存寻址，调试体验会提升不少。

## 可执行模块

OD的“可执行模块”窗口（ALT+E打开）显示的是==当前进程加载的所有可执行模块==，即主程序EXE文件及所有已加载的DLL动态库。

具体内容：

1. 模块名称：如 `sctrike.exe`、`kernel32.dll`、`user32.dll` 等。
2. 模块信息：每个模块的基地址、大小、入口点、路径等。
3. 双击跳转：双击某模块，可直接在CPU窗口中跳转至该模块代码区进行调试。

用途：`快速查看程序加载了哪些DLL`，在多个模块间切换调试，或确认某个模块是否被加载。调试加壳程序或分析依赖库时尤其有用。

> 模块包括扩展名通常为.EXE的可执行文件和启动时加载或动态加载的.DLL动态链接库。

## 线程窗口

OD的线程窗口（按T键打开）显示的是当前==被调试进程中的所有线程及其运行状态==，每行对应一个线程，可查看线程ID、线程入口地址、优先级、挂起状态等信息，并支持双击切换、挂起或恢复线程。

### 线程窗口里能看到什么

1. 线程标识：每个线程的ID和入口地址，入口指向线程函数起始位置。
2. 运行状态：当前线程是否在运行、被挂起或已结束，挂起线程右键选择“Resume all thread”恢复。
3. 优先级：线程调度优先级，如“32+0”“32-15”，影响CPU分配顺序。
4. 切换调试：双击某线程即可切换到该线程上下文继续调试，OD同一时间只跟一条线程执行。

### 和模块窗口的区别

- 线程窗口（T）：看“谁在跑”，列出进程内所有执行单元。
- 模块窗口（E）：看“加载了什么”，列出所有可执行文件和DLL模块，含基址、大小、入口点、完整路径。

多线程调试时，若断点能断下但按F7/F8直接跑飞，多半是目标线程被挂起，先去线程窗口检查状态再继续单步。

## 内存窗口

[内存布局与内存窗口关系](https://blog.csdn.net/qq_15895655/article/details/141460368)  

OD的内存模块窗口（按 `M` 键或点 `M` 按钮打开）显示的是当前被调试进程的整个内存布局，也就是==程序加载到内存后，所有可用的内存区块==（Region）的概览。

简单说，它是一张“内存地图”，让你看到==程序在内存里是怎么分布==的，每个区块的地址范围、大小、所属模块、区段名称和访问权限都能查到。

### 内存模块窗口里能看到什么

1. 代码段（.text）：存放程序的执行指令，通常属性是只读+执行（R-X），是反汇编窗口里看到的那些汇编代码的“老家”。
2. 数据段（.data /.rdata）：存放全局变量、常量、字符串等，`.rdata` 是只读数据，`.data` 可读写（RW-）。
3. 资源段（.rsrc）：存放图标、菜单、对话框等资源文件。
4. 堆（Heap）：程序运行时动态分配的内存区域，比如 `malloc` 或 `new` 分配的空间，属性是可读写（RW-）。
5. 栈（Stack）：存放函数调用时的临时数据、局部变量和返回地址，也是可读写（RW-）。
6. 动态链接库（DLL）：加载的每个 DLL 模块都会在内存中占据独立的区块，窗口里能看到它们的基址和大小，方便你分析跨模块调用。

### 这个窗口对调试有什么用

- 快速定位数据：想找某个变量或结构体在哪块内存，不用瞎猜，直接看内存布局就能锁定范围。
- 查看访问权限：比如想知道某个段是不是可写，或者代码段有没有被修改，一眼就能看出来。
- 分析模块加载情况：确认某个 DLL 是否加载成功、加载到哪个基址，有没有发生重定位，这对脱壳和逆向分析很关键。
- 配合数据窗口：在内存模块窗口选中某个区块，就能在数据窗口里查看该区块的具体内容（十六进制和 ASCII 两种形式）。

## 句柄窗口

OD的句柄窗口显示的是被调试程序当前打开的所有系统句柄，即==程序运行时持有的各种系统资源标识符==，如文件、线程、注册表键、互体量、事件等。

### 句柄窗口具体内容

- 句柄值：32位整数，系统内部标识资源对象。
- 对象类型：如File、Thread、Process、Event、Mutex等，告诉你资源是什么。
- 对象名称：某些内核对象有名称，如命名互斥量、事件，便于识别。
- 访问权限：程序打开该句柄时请求的操作权限。

### 为什么有用

- 排查资源泄漏：程序句柄数持续增长不释放，通常有泄漏。
- 分析程序行为：看程序打开了哪些文件、注册表项，推断其功能逻辑。
- 逆向分析辅助：结合API调用，理解程序对系统资源的操作流程。

> 句柄本质是系统资源的“间接引用”，不是直接内存地址，通过它操作系统统一管理资源访问，避免程序直接操作底层内存。

## 参考窗口

OD的参考窗口（R）显示的是你在调试过程中==搜索到的所有结果==，比如搜索的字符串引用、命令序列、常数或二进制内容等，方便快速定位和跳转到关键位置。

### 参考窗口具体能显示什么

- 字符串搜索结果：比如右键“中文搜索→搜索ASCII”后，所有匹配的字符串会列在这里，双击即可跳转到反汇编窗口中的对应地址。
- 命令/命令序列搜索结果：用 `Ctrl+F` 搜索特定汇编指令（如 `call`、`jmp`）或指令序列后，所有命中项会出现在参考窗口里。
- 常数或二进制搜索：搜索特定数值或二进制特征时，结果同样集中在此窗口，便于对比分析。
- 调用/被调用函数引用：查找==“谁调用了这个函数”或“这个函数调用了谁”==时，参考窗口会列出相关引用位置。

### 使用建议

参考窗口本质是结果汇总面板，配合 `Alt+F7` / `Alt+F8` 可在搜索结果间前后跳转，是逆向分析时定位关键代码的重要辅助工具。 若搜索后窗口没弹出，可试试按 `Alt+R` 手动打开。

## 函数入口点的标志指令

[55是函数的入口点_百度搜索](https://www.baidu.com/s?ie=utf-8&f=8&rsv_bp=1&tn=baidu&wd=55%E6%98%AF%E5%87%BD%E6%95%B0%E7%9A%84%E5%85%A5%E5%8F%A3%E7%82%B9&oq=%25E5%2587%25BD%25E6%2595%25B0%25E7%259A%2584%25E5%2585%25A5%25E5%258F%25A3%25E7%2582%25B9%252055&rsv_pq=b0119d87000fc91e&rsv_t=f29eM%2B73I1vVwjVquaxB8y%2F3cLkTpRwin6ck0j8gNuQKrwSOI5u9Lnn%2BjVY&rqlang=cn&rsv_enter=1&rsv_dl=tb_enter&rsv_sug3=7&rsv_sug1=4&rsv_sug7=100&rsv_n=2&rsv_btype=t&inputT=4882&rsv_sug4=4882)  

“55”在x86汇编里是 `push ebp` 的机器码，常作为函数入口点的标志指令，但“55”本身不是入口点，只是入口处常见的第一条指令。

### 为什么是55

x86环境下，函数开头通常先保存栈底指针，对应指令 `push ebp`，机器码为 `55`（十六进制）。

典型函数序言：

```assembly
55       push ebp          ; 保存调用者的栈帧基址
8B EC    mov ebp, esp      ; 设置当前函数的新栈帧
83 EC XX sub esp, 0xXX     ; 开辟局部变量空间
```

`push ebp` 是很多编译器生成的标准函数开头，故调试器和逆向分析时常用 `55` 定位函数入口。

### 注意区分

- 不是所有函数都以55开头：编译器优化后可能省略帧指针，或函数开头有其他指令，如 `push esi`、`sub esp, imm` 等。
- 55也可能是数据：单独看到 `55` 不一定是代码，可能是普通数据或字符串的一部分，需结合上下文判断。

###  实际应用

用调试器（如 OllyDbg{id="entity_1"}、IDA Pro{id="entity_2"}）分析程序时，可在反汇编窗口找 `55` 模式定位函数入口；在入口处下断点，即可观察函数调用过程、参数传递和返回值。

结合你之前看的PE结构和逆向分析内容，`55` 是函数入口的“指纹”，但真正入口点（Entry Point）是PE头里记录的地址，指向整个程序启动代码（如 `mainCRTStartup`），而非每个函数的 `push ebp`。

系统调用是应用程序向操作系统内核请求服务的接口，通过它程序才能获得读写文件、创建进程等需要高权限的操作能力。

### 系统调用是干啥的

1. 系统调用是操作系统提供给应用程序的一组特殊接口，程序通过它向内核发出服务请求。
2. 它的核心作用是让普通程序能够安全地使用硬件资源和系统服务，比如读写文件、网络通信、进程管理等。
3. 没有系统调用，应用程序就无法完成需要操作系统协助的任务，比如你写的程序想保存文件到硬盘，必须通过系统调用请操作系统帮忙。


### 为啥要分用户态和内核态

1. 系统调用运行时会发生状态切换：程序从用户态进入内核态，完成服务后再回到用户态。
2. 这样设计是为了安全：普通程序不能直接操作硬件，必须通过系统调用让操作系统代为处理，防止程序乱来搞坏系统。
3. 切换过程通过特殊指令实现，比如 x86_64 架构用 syscall 指令，参数通过寄存器传递，内核处理完后再用 sysret 指令返回。
4. 系统调用和普通函数调用的区别在于：普通函数一直在用户态运行，系统调用会进入内核态，所以开销更大。


### 常见系统调用有哪些

1. 进程控制类：创建进程（fork）、终止进程（exit）、获取进程信息（getpid）等。
2. 文件操作类：打开文件（open）、读取文件（read）、写入文件（write）、关闭文件（close）等。
3. 进程通信类：创建管道（pipe）、发送消息（send）、接收消息（recv）等。
4. 信息维护类：获取系统时间（time）、设置文件时间（utime）、获取系统信息（uname）等。

不是，系统调用和 Windows API 是两个层面的东西，不能画等号。 系统调用是用户程序请求操作系统内核服务的直接通道，而 Windows API 是微软提供给开发者的一组用户态函数接口，两者是“封装与被封装”的关系。

### 🪟 两者关系

1. Windows API 是“门面”：你写的程序调用 `CreateFile`、`MessageBox` 这些 API 时，实际执行的是 `user32.dll`、`kernel32.dll` 等动态链接库里的用户态代码。 这些 API 内部往往封装了更底层的系统调用，比如 `ReadFile` 最终会调用 `NtReadFile`，再通过 `syscall` 指令进入内核。

2. 系统调用是“内核入口”：在 x64 架构下，用户态程序执行 `syscall` 指令后，CPU 从 Ring 3 切换到 Ring 0，进入内核的 `KiSystemCall64` 函数，根据系统调用号在服务表中找到对应的内核函数执行。 系统调用号与 API 函数名不是一一对应，同一个 API 可能对应多个系统调用，不同 API 也可能封装同一个系统调用。

### 🔍 关键区别

- 层级不同：Windows API 属于用户态应用层接口，系统调用属于内核层接口，是用户空间与内核空间的交互边界。
- 调用机制不同：API 调用通常在用户态直接执行；只有封装了系统调用的 API 才会触发特权级切换（用户态→内核态）。
- 并非所有 API 都走系统调用：像 `abs()` 这样的纯计算函数完全不涉及内核，自然不会触发系统调用。

> 可以这样理解：Windows API 是“前台接待”，系统调用是“后台核心部门”。你找前台办事，前台可能自己解决，也可能转给后台——但前台不等于后台。

### 🧩 补充：Linux 对比

Linux 下也是类似设计，glibc 库函数（如 `write`、`open`）封装了系统调用，通过 `syscall` 指令陷入内核执行 `sys_write` 等函数。 这套“API 封装系统调用”的模式是操作系统设计的通用做法，并非 Windows 独有。
